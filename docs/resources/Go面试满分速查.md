## 1. Slice 底层原理与扩容

### 1.1 底层结构（切片头，24字节）
```go
type slice struct {
    array unsafe.Pointer // 指向底层数组的指针（8字节）
    len   int            // 长度：当前元素个数（8字节）
    cap   int            // 容量：底层数组可容纳的元素个数（8字节）
}
```
- slice 本身是**值类型**（拷贝的是这个3字段的头部），但**引用同一个底层数组**。
- 面试常问：`make([]int, 5, 10)` 和 `make([]int, 5)` 区别 → 前者 len=5/cap=10，后者 len=5/cap=5。

### 1.2 扩容规则（面试必考）
- **老版本（<1.18）**：扩容按 `newcap = oldcap*2`（容量小于1024时），`oldcap*1.25`（容量≥1024时，且不断向上调整）。
- **新版本（Go 1.18+）**：改进了扩容算法，当 `oldcap < 256` 时 `newcap = oldcap*2`；当 `oldcap >= 256` 时 `newcap = oldcap + (oldcap+3*256)/4`，即增长因子从 2 平滑过渡到 1.25。
- **关键点**：扩容是**创建新底层数组 + 拷贝数据**（copy），所以扩容后新 slice 和旧 slice **不再共享底层数组**。
- **关键点2（最容易考的坑）**：`append` 如果 `cap` 够，直接复用原底层数组、**不产生新数组**——这会导致两个 slice 共享底层数组、互相影响（见1.3）。

### 1.3 共享底层数组的坑（面试经典）
```go
a := make([]int, 5, 5)
b := a[1:3]        // b len=2 cap=4，共享 a 的底层数组
b[0] = 100         // 修改会影响 a[1]！因为共享同一底层数组
// 但 append 超过 cap 会触发扩容，产生新数组，a 和 b 才"解耦"
```
- `a[i:j:k]` 三切片语法可手动限制 cap：`b := a[1:3:4]` → b 的 cap=4-1=3。

### 1.4 append 细节
- `append(s, x...)` 追加一个 slice。
- `append` 返回值必须重新赋值给原变量（`s = append(s, x)`），因为可能换底层数组。
- `s = append(s, s...)` 可以自追加。

### 1.5 Slice 拷贝
- `copy(dst, src)` 返回实际拷贝的元素个数 = `min(len(dst), len(src))`，不会扩容 dst。
- 面试坑：`copy` 后若 dst cap 不够，只拷贝能放下的部分。

### 1.6 项目映射
- 在 Go 网关里拼接 RPC 响应切片时，注意是否共享底层数组（防止并发读写同一底层数组导致数据错乱）。
- 大量 append 的场景（如日志/埋点缓冲），提前 `make` 好 cap 避免频繁扩容。

## 2. Map 底层原理（hmap / bmap / 扩容 / 并发）

### 2.1 底层结构：hmap（哈希表 + 桶数组）
```go
type hmap struct {
    count     int     // 元素个数
    flags     uint8   // 状态标记（如正在扩容、迭代中）
    B         uint8   // 桶数 = 2^B
    noverflow uint16  // 溢出桶数量（近似）
    hash0     uint32  // 哈希种子（每个 map 随机，防哈希碰撞攻击）
    buckets   unsafe.Pointer // 桶数组（bmap 数组，长度 2^B）
    oldbuckets unsafe.Pointer // 扩容时旧桶数组（等量扩容/增量迁移用）
    nevacuate  uintptr        // 迁移进度（已迁移到第几个桶）
    extra     *mapextra       // 溢出桶/扩容预留
}
```
- map 本质是**哈希表 + 桶（bucket）**，桶数 = `2^B`。
- `hash0` 随机种子：每次创建 map 随机，防黑客构造冲突键（哈希碰撞攻击），这也是 map 无法用 `==` 比较的原因之一。

### 2.2 桶结构 bmap（一个桶存 8 个键值对）
```go
type bmap struct {
    tophash [8]uint8 // 存每个 key 哈希的高 8 位，加速查找（先比 tophash 再比 key）
    // 之后是：8个key、8个value（分开存储，key和value各自连续，利于内存对齐）
    // 末尾：overflow 指针 → 指向溢出桶
}
```
- **一个桶默认装 8 个键值对**；装满了再通过 `overflow` 指针挂**溢出桶**（链表）。
- **查找流程**：算出 key 哈希 → 用低 B 位定位到哪个桶 → 遍历桶内 8 个 tophash 比对（先比哈希高8位，相等再比 key 本身）→ 找不到去溢出桶链上找。
- 面试点：key 算哈希后 **"低 B 位定位桶，高 8 位（tophash）在桶内快速过滤"**。

### 2.3 扩容（面试核心）
触发条件（两个，满足其一）：
1. **装载因子 > 6.5**（`count / 2^B > 6.5`，即平均每个桶超过 6.5 个元素）→ **翻倍扩容**（B+1，桶数翻倍）。
2. **溢出桶太多**（`noverflow >= 2^B` 且 B<=15，或 noverflow>=32768）但装载因子不高 → **等量扩容**（桶数不变，把稀疏的键重新规整，减少溢出桶链）。

**增量迁移（重点）**：
- 扩容**不是一次性全部搬完**，而是**渐进式（增量）**：oldbuckets 保留，每做一次写/删操作时，顺带把一部分旧桶迁移到新桶（`nevacuate` 记录进度）。
- 读写时：key 在新桶找不到，会去 oldbuckets 找（查找时如果遇到未迁移的桶，也会触发迁移）。
- 好处：避免大 map 一次性扩容造成长时 STW / 卡顿，把开销摊到多次操作里。

### 2.4 并发安全（必考）
- **map 原生不支持并发读写**。多个 goroutine 同时写（或读写）会触发 **fatal error: concurrent map writes**（运行时直接 panic，不是死锁）。
- 为什么设计成这样？为了性能，单写场景不加锁。
- 解决方式（三选一）：
  1. `sync.RWMutex` 包一层（读多写少用 RWMutex 性能好）。
  2. `sync.Map`（读多写少 / key 稳定的场景，空间换时间，内部用 read 和 dirty 两个 map + 原子读）。
  3. 分片锁（shard map）：把 key 哈希分到 N 个 segment，每个 segment 一把锁，减少锁竞争。
- 面试常问：**sync.Map 适用场景**？→ 读多写少、且 key 稳定（写一次读很多次），如配置、缓存；不适合频繁写。

### 2.5 遍历无序
- map 遍历是**随机的**：Go 故意在遍历时从随机桶+随机偏移开始，防止依赖顺序。
- 所以不要依赖 map 遍历顺序；需要有序就排序 key 或用有序结构。

### 2.6 项目映射
- 在直播电商网关里做**去重/计数/聚合**（如按 region 聚合、按 skuId 去重）常用 map；高并发写场景（QPS 高）要小心 **map 并发写 panic**，正确做法是 `sync.Map` 或分片锁，而不是裸 map + 普通锁。
- 大 map 做缓存时，注意扩容的增量迁移代价；可预估容量 `make(map[K]V, n)` 提前分配桶数，减少扩容。

### 2.7 内置 map 扩容与扩容期间读写（小林 3.7/3.8，深挖）
**触发条件（满足其一）**：
1. **装载因子 > 6.5**（count / 2^B > 6.5）→ **翻倍扩容**（B+1，桶数×2）
2. **溢出桶太多**但装载因子不高 → **等量扩容**（桶数不变，重新规整，缩短溢出链）

**结构：新旧两个桶数组（平时只有一个，扩容期间并存）**
- `buckets`（新桶数组，长度 2^B）+ `oldbuckets`（旧桶数组，长度 2^B_old）
- `nevacuate`：下一个待搬迁的旧桶下标（进度游标）
- **翻倍扩容**：旧桶 i 按哈希第 B 位分成两拨 → 搬到新桶 **i** 和 **i + 2^B_old**
- **等量扩容**：旧桶 i → 新桶 i（桶数不变）

**增量搬迁（关键，避免一次性长停顿）**：
- 不是一次搬完，而是**边用边搬**：每次**写/删**操作，如果目标旧桶还没搬，先把**整个旧桶**迁到新桶（evacuate），再在新桶上操作，`nevacuate++` 推进
- 把 O(n) 搬迁成本摊到多次操作

**扩容期间读写规则（必背）**：
- **读**：算出目标桶后 → 若旧桶 index < nevacuate（已搬迁）→ **只查新桶**；否则 → **先查旧桶**，找不到**再查新桶**（兜底半搬状态）
- **写/删**：若目标旧桶未搬迁 → **先触发该桶搬迁** → 再在新桶上写/删
- 全部搬完 → `oldbuckets` 置 nil，只剩新桶数组

> 记忆：与 **Redis 渐进式 rehash** 同一思想（新旧两张表 + 进度游标 + 访问时顺带迁移），面试可对比讲。
## 3. Channel 底层原理（hchan / 发送接收 / 缓冲 / 关闭）

### 3.1 底层结构 hchan
```go
type hchan struct {
    qcount   uint   // 队列中当前元素个数
    dataqsiz uint   // 环形缓冲区的容量（cap），无缓冲=0
    buf      unsafe.Pointer // 环形缓冲区（存放元素的内存）
    elemsize uint16
    closed   uint32 // 是否关闭
    sendx    uint   // 发送游标（下一个写入位置）
    recvx    uint   // 接收游标（下一个读取位置）
    recvq    waitq  // 等待接收的 goroutine 队列（阻塞在"读"）
    sendq    waitq  // 等待发送的 goroutine 队列（阻塞在"写"）
    lock     mutex  // 一把互斥锁保护整个 channel
}
```
- **有缓冲 channel** = 环形缓冲区（buf）+ 两个等待队列（sendq/recvq）。
- 所有操作都要先加 `lock`，所以 **channel 本身是并发安全的**（这点和 map 不同）。

### 3.2 发送（send）流程
1. 加锁。
2. 先看 **recvq 是否有等待接收者**：
   - **有** → 直接**把值交给这个等待的 goroutine**（不经过 buf），唤醒它。这叫"直接发送"。
3. recvq 空，再看 **buf 有没有空位**（qcount < dataqsiz）：
   - **有空位** → 写入 buf 的 sendx 位置，sendx 前进，qcount++。
4. buf 满了 → 当前 goroutine **被阻塞**，打包成 sudog 挂到 **sendq**，让出 CPU（gopark），等接收者来唤醒。

### 3.3 接收（recv）流程（对称）
1. 加锁。
2. 先看 **sendq 是否有等待发送者**：
   - **有** → 直接从发送者那里拿值（或从 buf 队头拿一个，再把发送者的值放进队尾），唤醒发送者。
3. sendq 空，看 **buf 是否有数据**（qcount > 0）：
   - **有** → 从 buf 的 recvx 取，recvx 前进，qcount--。
4. buf 空 → 当前 goroutine 阻塞，挂到 **recvq**，等发送者唤醒。

### 3.4 无缓冲 vs 有缓冲（核心区别）
- **无缓冲**（`dataqsiz=0`）：buf 为空，发送和接收**必须同时配对**才能完成。发送者若没有接收者，发送阻塞；反之亦然。→ 常用于**同步**（goroutine 之间握手）。
- **有缓冲**：发送者只要 buf 有位置就立即返回（非阻塞），不要求接收者同时就绪。→ 常用于**解耦/限流**（如任务队列）。

### 3.5 关闭 channel（必考坑）
- **向已关闭的 channel 发送 → panic**（`send on closed channel`）。
- **从已关闭的 channel 接收**：先把 buf 里剩的读完，之后**返回零值**（不 panic）。所以用 `v, ok := <-ch` 的 `ok` 判断是否已关闭（ok=false 表示关闭且读完）。
- **重复关闭 → panic**；关闭 nil channel → panic。
- **关闭 channel 的职责**：只能由**发送方**关闭，不能由接收方关闭，否则易造成向已关闭 channel 发送 panic。
- 通过 channel 结束 goroutine 的经典写法：`for v := range ch`，channel 被 close 后 range 自动退出。

### 3.6 channel 会不会死锁 / 泄漏
- **无接收者、无缓冲、一直 send → 死锁**（所有 goroutine 阻塞）。
- **goroutine 泄漏**：发送方阻塞在 sendq 上没人接收，或接收方阻塞在 recvq 上没人发送，且没人 close → 这些 goroutine 永远阻塞，泄漏。
- 排查：pprof 看 goroutine 数量 / channel 阻塞点。

### 3.7 项目映射
- 直播电商网关：**有缓冲 channel 做任务队列/限流**（如把落库/埋点任务投递到 worker，worker 消费），用有缓冲 channel 解耦主链路和异步任务，避免阻塞请求。
- **优雅退出**：主 goroutine close channel 通知 worker 退出，worker 用 `for task := range ch` 收尾。
- 注意：高并发下 worker 池 + channel 消费，要考虑 channel 容量和 worker 数匹配，避免 goroutine 阻塞堆积。


## 4. GMP 调度模型（小林 9.1-9.10）

### 4.1 GMP 是什么（9.1）
- **G** = goroutine（协程），轻量级用户态协程。
- **M** = machine（系统线程），真正干活的执行体。
- **P** = processor（逻辑处理器），G 和 M 之间的"桥梁"，负责调度。
- **核心规则**：M 必须**绑定 P** 才能执行 G。每个 P 维护自己的**本地队列 LRQ（长度 256）**，M 从 P 的本地队列取 G 执行。
- 本地队列空时，M 按优先级从 **全局队列 GRQ → 网络轮询器 netpoll → 其他 P 的队列（work-stealing 偷取）** 找 G。
- 作用：用**少量线程调度海量 goroutine**，是 Go 高并发的基础。

### 4.2 Go scheduler（9.2）
- Go scheduler 是 Go runtime 的**协程调度器**，内嵌在 Go 程序里一起运行。
- 核心是 `schedule()` 函数：无限循环找可运行 G → `execute()` 切换到 G 执行 → G 让出/被抢占后再回到调度循环。

### 4.3 调度策略：抢占式调度（9.3，必考）
- Go 会启动 `sysmon` 监控线程（跑在 M 上，不需要 P），发现同一个 G 运行超过 **10ms** 就标记抢占。
- **Go 1.14 之前**：协作式抢占——编译器在函数调用入口插入检查代码，G 进行函数调用时检查 preempt 标志。**缺陷**：没有函数调用的大循环（如 `for{}`）永远不被抢占，会霸占 M，导致同 P 队列其他 G 饿死（调度延迟）。
- **Go 1.14 之后**：**基于信号的异步抢占**——sysmon 向运行超时 G 的 M 发 **SIGURG 信号**，M 上的 `gsignal` 处理信号并停止该 G。解决了大循环无法抢占的问题。
- 面试点：`for {}` 空循环在 1.14+ 可以被抢占，但要注意它仍会占用 CPU（GOEXPERIMENT=preemptibleloops 时代之后，1.14 起可抢占）。

### 4.4 调度时机（9.4）
- 等待读写**未缓冲的 channel**
- `time.Sleep()`
- 等待**互斥锁**释放
- 发生**系统调用**
- 补充：G 运行超 10ms 被 sysmon 抢占；主动调用 `runtime.Gosched()` 让出。

### 4.5 M 找可运行 G 的过程（9.5，必考顺序）
1. 先从**当前 P 的本地队列 LRQ** `runqget`（**无锁 CAS**）
2. 没有 → **全局队列 GRQ** `globrunqget`（**需要加锁**）
3. 没有 → **网络轮询器 netpoll**（非阻塞，看有没有网络 IO 就绪的 G）
4. 没有 → **从别的 P 偷（work-stealing）**：随机找一个 P，从它 LRQ 偷**一半** G 过来

> 记忆：**本地(无锁) → 全局(加锁) → netpoll → 偷取**。前两步有锁差异是面试点。

### 4.6 为什么不能去掉 P 层（9.6）
- 去掉 P 变回 GM 模型：所有 M 都要从**全局队列**取 G，需要**全局锁**保护。高并发下大量 M 争抢同一把锁 → 严重锁竞争 → CPU 浪费在等锁上。
- **P 的价值**：实现**无锁本地调度**——M 绑定 P 后直接从本地队列取 G，大部分情况不需要全局锁；只有本地队列空了才去偷。
- 面试点：P 让本地调度无锁化，是性能关键。

### 4.7 P 和 M 何时创建（9.7）
- **P**：调度器初始化时**一次性创建**（`schedinit()` 里 `procresize()` 按 `GOMAXPROCS` 创建，存全局 `allp` 数组）；只有调 `runtime.GOMAXPROCS()` 才会动态调整。
- **M**：**按需创建**。初始只有 m0；当所有 M 都在阻塞的系统调用、或没有空闲 M 绑定 P 时才 newm() 创建。M 数量上限 `sched.maxmcount`（默认 10000），可用 `runtime/debug.SetMaxThreads()` 调整。

### 4.8 m0（9.8）
- Go 启动时创建的**第一个 M**，对应**主系统线程**，整个生命周期都在。
- 负责启动流程：调度器/内存管理器/GC 初始化，创建并运行第一个用户 goroutine 执行 `main.main`；退出时做清理。

### 4.9 g0（9.9）
- 每个 M 都有一个自己的 **g0**（调度协程），不是普通用户协程。
- 使用系统线程原始栈（8KB），不像普通 G 用可增长分段栈。
- 职责：**执行调度逻辑**（G 的创建/销毁/调度决策）、处理 GC/栈扫描/信号。
- 为什么需要：调度器代码不能在普通 goroutine 栈上执行（会栈冲突/递归调度），g0 提供独立执行环境。

### 4.10 g0 和用户栈切换（9.10）
- 本质是 **SP 寄存器 + 栈指针切换**。
- 用户 G 需要调度 → `mcall()` 切到 g0：保存用户 G 的 PC/SP 到其 `gobuf`，SP 指向 g0 栈，PC 指向调度函数。
- 调度完 → `gogo()` 从 g0 切回用户 G，恢复寄存器。
- 逻辑在汇编实现（`runtime·mcall` / `runtime·gogo`），保证原子性和高效。

### 4.11 项目映射
> 直播电商网关高并发：**goroutine 数远大于线程数**，一个 M 上可跑成千上万 G，天然适合处理大量并发请求（如秒杀/竞拍瞬时流量）。
> 注意：有阻塞系统调用（如同步 DB/RPC 调用）会占住 M，要控制并发上限（如信号量/worker 池），避免创建过多 M 导致线程暴增；用 channel + worker 池比无限 go 更可控。


## 5. 垃圾回收 GC（小林 11.1-11.14）

### 5.1 常见 GC 实现方式（11.1）
- 两大类：**追踪式（Tracing）** 和 **引用计数（Reference Counting）**。
- 追踪式变种：标记清扫 / 标记整理（解决碎片）/ 增量式（分批执行减少停顿）/ 分代式（按存活时间分年轻代/老年代）。
- 引用计数：计数归零立即回收（如 Python、Swift 早期），缺点：循环引用。

### 5.2 Go 用的 GC（11.2）
- **无分代、不整理、并发** 的**三色标记清扫算法**。
- 无分代：对象不分代际；不整理：不移动对象（避免对指针的额外处理）；并发：与用户代码并发执行。

### 5.3 三色标记法（11.3）
- **白**：未被访问（结束后被清理，即垃圾）。
- **灰**：已被访问、但其引用对象还未完全扫描（待处理队列，即"波面"）。
- **黑**：已被访问且所有引用都扫描完（确认存活）。
- 流程：GC 开始全白 → 从 **GC Root**（全局变量/栈变量）开始把直接可达标灰 → 反复取灰对象、扫其引用，白→灰，扫完变黑 → 直到灰队列为空 → 只剩黑(存活)和白(垃圾)。

### 5.4 GC 根对象（11.4）
- **全局变量**、**执行栈**（每个 goroutine 栈上的变量+指向堆的指针）、**寄存器**。

### 5.5 STW（11.5）
- Stop The World：用户代码完全停止运行。STW 越长，延迟影响越大。早期 Go 可达几百毫秒；现在的目标是**微秒级**。

### 5.6 并发标记清除的难点（11.6）
- **对象消失问题（核心）**：黑色对象**已扫描完不会再扫**。若在标记期间，赋值器**新增了一条"黑色→白色"的引用**（黑色不会重扫，这条路径不会被标记），**同时删除了"灰色→该白色"的引用**（原保护路径断了），则该白色对象实际上仍从黑色可达，却永远不会被标记 → **被误回收**。
  - 关键点：问题出在"**新增黑→白**"+"**删除灰→白**"同时发生，导致白色失去灰色保护、又因黑色已扫过而漏标。
- **新对象处理**：标记期间新分配对象如何着色——标白可能被误回收，标黑可能成"浮动垃圾"。

### 5.7 解决方案：写屏障 + 三色不变性（11.7）
- **弱三色不变性**：允许黑色指向白色，但必须保证该白色有一条从**灰色**出发的可达路径（被灰色"保护"）。
- **混合写屏障**：指针赋值时，新建引用把目标标灰、删除引用把被删对象标灰，确保关键对象不丢。
- **栈不写屏障**：栈操作频繁、开销敏感，标记开始/结束时分别扫描栈，中间不加写屏障（栈被当作黑色）。
- 结果：微秒级 STW，大部分 GC 与用户程序并发。

### 5.8 写屏障细节（11.8）
- 写屏障本质：编译器在 `*slot = ptr` 指针赋值处插入的额外短指令。
- **Dijkstra 插入写屏障**：建新引用时标目标为灰；删引用无保护。
- **Yuasa 删除写屏障**：删引用时标原对象为灰；建引用无保护。
- **Go 1.8 混合写屏障**：指针写入时**同时**把被覆盖旧对象 `*slot` 和新指向对象 `ptr` 都标灰；GC 标记阶段栈上所有新对象默认标黑 → 避免再次 STW 重扫栈。

### 5.9 GC 流程（11.9）
| 阶段 | 说明 | 状态 |
|---|---|---|
| SweepTermination 清扫终止 | 为并发标记做准备，启动写屏障 | STW |
| Mark 标记 | 与赋值器并发执行，写屏障开启 | 并发 |
| MarkTermination 标记终止 | 保证标记完成，停止写屏障 | STW |
| Sweep 清扫 | 把可回收内存归还堆 | 并发 |
| 内存归还 | 过多内存归还 OS | 并发 |

### 5.10 GC 触发时机（11.10）
- **主动**：`runtime.GC()`（阻塞等待跑完）。
- **被动**：
  1. 系统监控线程发现**超过 2 分钟无 GC** → 强制触发。
  2. **堆增长阈值**：每次分配检查，堆达到上次标记堆大小的 **GOGC%（默认 100%，即翻倍）** 时触发；`debug.SetGCPercent(500)` 可调。**第一次 GC 触发临界值 4MB**。

### 5.11 GC 关注指标（11.11）
- **CPU 利用率**、**GC 停顿时间（STW + Mark Assist）**、**停顿频率**、**可扩展性**。

### 5.12 有 GC 为何还内存泄漏（11.12）
1. 内存被**根对象引用**而未迅速释放（如局部变量被赋值到全局 map）。
2. **goroutine 泄漏**：goroutine 不退出，其引用对象一直可达。

### 5.13 GC 调优（11.13）
- 合理化分配速度、提高赋值器 CPU 利用率。
- **降低并复用内存**：`sync.Pool` 复用频繁创建的对象。
- **调 GOGC** 调大，让 GC 触发更晚、频率更低，提高机器使用率（但堆占用变大，需权衡）。

### 5.14 观察 GC（11.14）
- `GODEBUG=gctrace=1` 运行，看 `gc N @ t 2%: 0.009+0.23+0.004 ms clock, ... , 4->6->2 MB, 5 MB goal, 12 P`：
  - `4->6->2` = 标记开始时堆大小 / 标记结束时堆大小 / 存活对象大小
  - `0.009`=标记开始 STW，`0.23`=并发标记，`0.004`=标记终止 STW
  - `5 MB goal` = 触发目标，`12 P` = P 数量
- `scvg`：内存归还给 OS 的日志。

### 5.15 项目映射
> 直播电商网关：高并发下频繁创建对象（如每秒大量请求的反序列化对象）会给 GC 压力 → 用 **sync.Pool 复用** + 预分配容量减少分配。
> GC 调优用 GOGC 权衡：网关要低延迟 → 适度调大 GOGC 减少 GC 频率；但要监控堆内存，别让 heap 涨太猛。用 `GODEBUG=gctrace=1` / pprof 观察 GC 指标。


## 6. Sync 锁 / 原子（小林 5.1-5.13）

### 6.1 除 Mutex 外的并发安全方式（5.1）
- **信号量**（semaphore）：计数控制，实现和 mutex 类似。
- **Channel**（Go 推崇）：通过通信传递数据所有权，从根源避免竞争，适合复杂业务。
- **原子操作 atomic**：针对整型/指针的无锁操作，性能最高，常用于计数器/状态位。
- 选择依据：数据结构复杂度 + 业务读写模型。

### 6.2 原子操作怎么实现（5.2）
- 底层依赖 **CPU 硬件原子指令**（不是 OS/锁）。
- `sync/atomic` 函数编译时被识别，直接转成单条原子机器指令：x86 上 `atomic.AddInt64` → `LOCK; ADD`，`LOCK` 前缀锁总线/缓存行，保证操作期间其他 CPU 核不能访问该内存。

### 6.3 原子操作 vs 锁（5.3）
| | 原子操作 | 锁 |
|---|---|---|
| 层级 | CPU 硬件层（微观） | OS/运行时（宏观） |
| 保护范围 | 单个数据（整型/指针）单次读写 | 一个**代码块/临界区**（多变量逻辑） |
| 获取失败 | 不挂起（自旋/继续） | goroutine 休眠 |
| 开销 | 极低 | 高 |
- 结论：简单计数器/标志位用原子；多变量或一段逻辑必须用锁。

### 6.4 Mutex 底层实现（5.4）
```go
type Mutex struct {
    state int32 // 锁状态（锁定/唤醒/饥饿模式，用二进制位标识）
    sema  uint32 // 信号量，定位阻塞队列，实现 goroutine 阻塞/唤醒
}
```
- **原子操作 + 信号量**：用 atomic 实现锁定，用信号量实现阻塞与唤醒。

### 6.5 Mutex 两种模式（5.5，必考）
- **正常模式（默认，性能优先）**：新来的 goroutine 和等待队列头部**竞争**，新来的有机会**自旋**抢锁 → 吞吐高但"不公平"（队头可能等很久）。
- **饥饿模式（公平优先）**：等待队列中的 goroutine 等待超 **1ms** 就切到饥饿模式；锁释放后**直接移交给队头**，新来的不参与竞争、排到队尾 → 防止"饿死"。
- 切换回正常：等待队列空，或拿到锁的 goroutine 等待时间 < 1ms。
- 记忆：**正常模式 = 性能/不公平（允许插队自旋）；饥饿模式 = 公平（排队 1ms 触发）**。

### 6.6 自旋会不会占用太多资源（5.6）
- 不会。自旋**有严格次数和时间限制**（几十纳秒），且只在特定条件发生（CPU 核数 >1、机器不算忙、没有太多 goroutine 排队）。
- 本质：**机会主义短线优化**——用极小 CPU 开销避免一次昂贵的"挂起+唤醒"上下文切换；锁竞争不激烈、占用时间极短时反而省资源。

### 6.7 锁释放后谁先拿到（5.7）
- **正常模式**：唤醒队列头，但**不一定**拿到——新来自旋的 goroutine 可能插队成功（吞吐高、可能饿死队头）。
- **饥饿模式**：锁**直接移交给队头**，新来的必须排队尾（绝对公平）。

### 6.8 sync.Once（5.8）
- 作用：确保函数**只执行一次**（单例初始化/一次性全局配置加载）。
```go
type Once struct {
    done uint32 // 标识位（是否执行过）
    m    Mutex
}
```
- 原理：**原子快速检查 + 双重检查锁定（DCL）**——`atomic.LoadUint32(done)` 为 1 直接返回（无锁路径）；为 0 则加锁 → **再次检查 done** → 执行 f → `atomic.StoreUint32(done, 1)`。双重检查防止多个 goroutine 同时进入时 f 被重复执行。

### 6.9 WaitGroup（5.9）
- 本质：**原子计数器 + 信号量**。Add 加计数、Done 减计数、Wait 检查计数器，非 0 就信号量挂起；最后一个 Done 清零后**一次性唤醒所有 Wait 者**。
```go
type WaitGroup struct {
    noCopy noCopy         // 防止被拷贝（go vet 检查）
    state  atomic.Uint64  // 高32位=计数器counter，低32位=等待者数量waiter
    sema   uint32         // 信号量，阻塞/唤醒
}
```

### 6.10 sync.Map 底层（5.10-5.12）
- 核心：**空间换时间**，双 map 结构实现"读写分离"，让**读操作无锁**。
```go
type Map struct {
    mu     Mutex                 // 保护 dirty
    read   atomic.Value          // 只读 map（readOnly 结构，无锁读）
    dirty  map[interface{}]*entry // 需加锁的完整 map
    misses int                   // read 未命中次数，misses==len(dirty) 时 dirty 晋升
}
type readOnly struct {
    m       map[interface{}]*entry
    amended bool // dirty 是否有 read 没有的新数据
}
type entry struct { p unsafe.Pointer } // 指向真正的 value
```
- **read（只读缓存）**：无锁并发读；**dirty（最新全集）**：加锁写。读 miss 累计到 misses==len(dirty) 时 dirty **晋升**为新 read。
- **nil vs expunged 两种删除状态（5.12）**：read 是只读的不能直接删 key → Delete 时用原子把 `entry.p` 置 **nil**（逻辑删除）；当需要基于 read 重建 dirty 时，把 p==nil 的 entry 进一步标 **expunged**（表示"不再复制到新 dirty"，物理删除推迟到晋升那一刻）。重新 Store 一个 expunged key 要先回退为 nil 并同步到 dirty。→ 用状态标记换取无锁性能。

### 6.11 sync.Map 适用场景（5.13）
- **读多写少**（把流量尽量在 read 层无锁拦截）；**不适合写多读少**——写多时退化成"互斥锁+map"，效率大降。
- 例：配置、缓存（写一次读多次）。

### 6.12 项目映射
> 直播电商网关：**计数器/限流/状态位**用 `atomic`（如 QPS 计数器、并发数）；**多变量一致性**用 Mutex；**只初始化一次的组件**（如全局配置、单例 SDK）用 `sync.Once`；**等待一批 goroutine 收尾**（如聚合多路下游返回）用 `WaitGroup`；**读多写少的配置/字典缓存**用 `sync.Map`。
> 注意：网关对延迟敏感，锁竞争激烈时优先考虑分片锁/原子/Channel 替代全局 Mutex。


### 6.13 sync.Map 深挖补全（对话问答沉淀，防混淆用）

**read / dirty 关系（共享 entry 指针）**：
- read 和 dirty 都是 `map[interface{}]*entry`，存的是 **"key → entry 地址（指针）"**，不是值本身
- 晋升/重建时拷贝的是**同一批 `*entry` 指针** → 两个 map 里相同的 key 指向**同一个 entry 对象**
- **dirty = 全集**（最新最全）；**read = "上次晋升时的快照子集"**：read 有的 dirty 一定有（共享 entry），dirty **新增的 key read 暂时没有**（`amended=true` 标记差异）
- **增量 key 只进 dirty**；读 miss 累计（`misses >= len(dirty)`）触发**晋升**：dirty 整体拷成新 read，dirty 置 nil

**为什么改 entry 不用加锁（关键认知）**：
- map 里存的只是 8 字节**地址**；entry 是**地址指向的独立堆对象，不在 map 桶里**
- 类比：**map = 电话簿（人名→门牌地址），entry = 房子**
  - **操作 map** = 改电话簿（插入/删除一行、重抄）→ 动哈希表结构 → 必须加锁
  - **改 entry** = 走到房子内部刷漆 → 电话簿一个字没动 → 用**原子 CAS** 即可
- CAS 是原子指令，本身线程安全：两个 goroutine 同时 CAS 同一 entry.p 不会 panic（一个成功、一个失败重试）

**Store 三条路径（必背）**：
1. key 在 read 且 `p != expunged`（已有 key）→ **CAS(entry.p, 旧→新)**，无锁 ✅（read/dirty 共享 entry，同时生效）
2. key 在 read 但 `p == expunged`（彻底删除过）→ **加锁**，把 entry 从 expunged 恢复回 dirty（哨兵不能 CAS）
3. 新 key（read/dirty 都没有）→ **加锁写 dirty**；若 dirty==nil（刚晋升过）先拷 read 重建 dirty（**排除 expunged**），置 `amended=true`

**为什么不会并发写 panic**：
- `read` 结构从不就地改，只整体 `atomic.Value.Store` 换新快照
- `dirty` 只在 mu 锁内写
- `entry.p` 用 CAS 原子改（不是 map 写操作）
→ 内置 map 的并发写检测永远不触发

**nil vs expunged（删除状态）**：
- **nil** = 逻辑删除：读返回 nil,false，**槽位还在 read**，可**无锁复活**（CAS nil→新值）
- **expunged** = 彻底删除：重建 dirty 时被排除，**复活必须加锁**（先恢复回 dirty）
- 为什么能无锁删：删除 = CAS entry.p 置 nil，一次原子操作，不动 map 结构
- 流程：Delete 先 CAS 置 nil（无锁）→ 重建 dirty 时 p==nil 的 entry 升级为 expunged 且不复制 → 物理删除推迟到晋升时刻
