## 一、大模型基础（必问，面试第一个问题区）

### Q1：解释一下 Self-Attention？为什么要除以 √d_k？
**满分答案框架**：
> **核心本质**：解决RNN/LSTM串行不能并行问题，让所有词同时计算，GPU利用率更高，能捕捉长距离依赖。
>
> **数学公式：** `Attention(Q,K,V) = softmax(QK^T/√d_k) · V`
>
> 每个词通过三个线性投影得到三个向量：
> - Q (Query)："我要找什么信息，我查询谁"
> - K (Key)："我有什么信息，别人可以来查我"
> - V (Value)："我的信息是什么"
>
> Q 和所有 K 做点积得到注意力分数（就是相似度，越相似分数越高）。
>
> **为什么除以 √d_k？**
> 假设 Q 和 K 每个元素是均值0方差1，点积方差就是 `d_k`（sum 乘积方差就是d_k倍单个方差）。除以 √d_k 后方差回到1，避免softmax分数太极端（大部分概率堆到少数几个点），保持梯度稳定，让模型容易训练。
>
> **Multi-Head Attention（多头）**：
> - 把Q/K/V切分成h个小头，每个头维度是 `d_k = d_model / h`，每个头单独算一遍Self-Attention
> - 最后把所有头输出拼起来，乘一个投影矩阵得到最终输出
> - 为什么要多头：不同的头能学到不同的注意力模式，同一个词能同时关注句子里不同位置的不同语义关系（比如指代消解，一个头关注先行词位置，一个头关注动词关系），表达能力更强。
>
> 最后把所有头输出拼起来乘以投影矩阵，得到和输入维度一样的最终输出，总参数量没变，只是多了一次切分和拼接，代价很小，提升明显。

**手算例子（3个词、d=2，完整展示流程）**

以句子"我 喜欢 你"为例，维度d_k=2，Wq/Wk/Wv简化为2×2矩阵：

1. **每个词初始Embedding**：x_我=[1,0]，x_喜欢=[0,1]，x_你=[1,1]
2. **算Q/K/V**：每个词x乘Wq/Wk/Wv得到Q/K/V，例如Q_我=x·Wq=[1,0]，K_我=[0,1]，V_我=[1,0]
3. **点积算分数**：每个词的Q和所有词的K点积（对应元素相乘相加），Q·K越大表示越相关
   - "我"的分数 = [Q_我·K_我=0, Q_我·K_喜欢=1, Q_我·K_你=1]
4. **Softmax归一化**：分数变权重，加起来=1
   - "我"的权重 = softmax([0,1,1]) ≈ [0.16, 0.42, 0.42] → 表示"我"融合信息时42%来自"喜欢"、42%来自"你"
5. **加权求和**：输出 = 0.16×V_我 + 0.42×V_喜欢 + 0.42×V_你 = [1.0, 0.84]
   - 原始"我"是[1,0]，新表示融合了"喜欢"和"你"的V向量信息，第二个维度从0变成0.84，就是吸收了上下文

**白话理解**：
- Q是"我要找谁"，K是"我的特征"，V是"我的信息"
- 点积Q·K = 匹配度（你和我像不像）
- Softmax = 匹配度转成百分比权重
- 加权求和 = 按权重吸收相关词的信息
- 最终每个词都变成融合了上下文的新向量，这就是"自注意力"理解上下文的原理

**实战对应**：如果你做过模型微调，说："我微调 LLaMA 时看过源码，Self-Attention 部分确实就是这么实现，我还对比过 RoPE 对精度影响"。

### 追问必背（100%会问）

**1. 完整 Self-Attention 计算流程（手算级别）**
以3个词d=2为例：
1. 输入 X 乘 W_Q/W_K/W_V 三个可学习矩阵，得到 Q/K/V 向量
2. 点积：score(i,j) = Q_i · K_j（相似度，Q是"我找什么"，K是"我有什么"）
3. 缩放：除以 √d_k，防止维度大点积过大Softmax饱和梯度消失
4. Softmax：每行 exp/Σexp，归一化成权重 α（每行和=1）
5. 加权求和：O_i = Σ_j α_ij · V_j，每个词的输出是所有词V的加权平均，权重视相关性

**2. 为什么多头（Multi-Head）？**
- 类比多路召回：单头只能学一种相似关系，分头并行学不同子空间（语法/语义/位置）
- h个头，每头 d_k = d_model/h，总计算量和单头相同
- 每个头独立有自己的 W_Q/W_K/W_V，算完 Concat 再乘 W_O 融合
- 工程上一次大矩阵乘法并行完成，不增延迟

**3. KV Cache（推理加速核心，必问）**
- **问题**：自回归生成第t个token时，前t-1个token的K/V重复计算
- **解法**：历史token的K/V是不变的（因为输入已定），prefill阶段把所有prompt的K/V算好缓存，decode阶段每步只算新token的K/V并append
- **加速效果**：单步decode从O(n²)→O(n)，整体O(n³)→O(n²)
- **显存代价**：KV_cache = 2×n_layers×n_kv_heads×d_head×seq_len×batch×2字节
  例：Llama2-7B seq=4096 batch=1 ≈ 2GB；batch=32 ≈ 64GB，是显存主要瓶颈

**4. MHA vs MQA vs GQA（省显存设计）**
| 模式 | Q头 | KV头 | 代表 | KV显存 | 效果 |
|---|---|---|---|---|---|
| MHA | h | h | BERT/GPT-3 | 1x | 最好 |
| MQA | h | 1 | PaLM | 1/h 最省 | 掉点明显 |
| GQA | h | h/k 分组 | **Llama2-70B(32Q/8KV)**、Qwen、Mistral | 1/k 折中 | **几乎不掉点** ✅ |
- GQA是当前大模型推理优化主流：KV Cache显存降k倍，吞吐提升2-3倍，效果损失极小

**5. RoPE旋转位置编码**
- 老办法（BERT/GPT-2）：可学习绝对位置embedding，不能外推长度
- RoPE：对Q/K每两维看成2D点，按位置m旋转θ角，旋转后点积只依赖**相对位置差**
- 优势：天然相对位置感知 + 支持长度外推（NTK/YaRN插值，4K训的模型扩到128K）
- 主流模型（Llama/Qwen/Mistral）全用RoPE

**面试金句**："Transformer推理成本大头是KV Cache显存，所以现代模型普遍用GQA省KV Cache，RoPE支持长上下文外推，推理框架如vLLM用PagedAttention解决KV显存碎片问题。"

### Q2：RAG 完整链路说一遍？每个环节怎么做优化？
**满分答案框架（按顺序说，有结构）**：

```
[索引阶段]
  文档加载 → 文档切片 → Embedding → 向量存储
[推理阶段]
  用户提问 → Query预处理 → 检索 → Rerank → Prompt拼接 → LLM生成 → 后处理 → 返回
```

**每个环节面试要点 + 实战点**：

| 环节 | 高频面试点 | 满分答法 | 简历写什么 |
|------|------------|----------|-----------|
| **切片 Chunking** | 怎么选 chunk size？为什么要 overlap？ | 固定大小 256~1024 tokens，overlap 10%~20%，防止切断语义。进阶：递归字符切片优先切自然边界（段落→句子），语义切片找相似度断点。生产常用父子文档（小块检索大块生成）。 | 项目中对比了 256/512/1024 三种 chunk size，在我司知识库上 512 最优，Recall@5 提升了 8% |
| **Embedding** | BGE-M3 为什么好用？ | BGE-M3 支持多语言、长文档、多粒度嵌入，国内开源第一梯队，效果比 OpenAI text-embedding-3 差一点但免费可部署。中文场景优先 BGE-M3/M3E。 | 项目中替换旧 embedding 为 BGE-M3，Recall@5 从 78%→86% |
| **检索** | 混合检索怎么做？ | 向量擅长语义匹配，BM25 擅长精确关键词匹配，两路召回后用 RRF（Reciprocal Rank Fusion）融合排名，不调权重泛用性好。 | 实现了混合检索，相比纯向量 Recall@5 又提升了 5% |
| **Rerank** | 为什么需要 Rerank？ | 多路召回选出 Top20 后，用 Cross-Encoder（把 query+doc 一起喂给模型）精排，计算量大但精度高，能大幅提升 precision@k。常用 bge-reranker-v2-m3。 | 项目中加了 Rerank，最终回答 Faithfulness 提升了 12% |
| **Query 优化** | 最常用的优化方法 | ①HyDE：先生成假设答案，用假设答案检索；②Multi-Query：生成多个角度查询并行检索；③Step-Back：先抽象问题再检索；④Query 改写：多轮对话做指代消解。 | 我在项目中集成了 HyDE + Step-Back，解决了问题语义模糊漏检问题 |
| **幻觉** | 怎么减少 RAG 幻觉？ | ①Prompt 强约束：只回答上下文里有内容；②强制引用来源，让模型标出来源段落；③Faithfulness 校验：生成后用 LLM-as-Judge 校验是否每个事实都来自上下文；④不相关上下文直接返回不知道。 | 实现了 LLM-as-Judge 自动检测幻觉，幻觉率从 18%降到 5% |

**追问必背**：
> Q：Graph RAG 是什么？解决什么问题？
> A：微软提出，先从文档抽实体/关系建知识图谱，然后基于图遍历回答全局问题（如总结全文观点），解决传统 RAG 对跨文档全局查询差的问题。缺点是抽取成本高、复杂知识图谱维护难。适合全局知识问答，不适合问答具体文档片段。
>
> Q：Agentic RAG 是什么？
> A：让 Agent 自主决策检索流程——判断问题需要检索吗？检索不对需要改写再检索吗？多轮检索直到拿到足够信息再回答。比传统固定一次检索效果好，但是增加延迟和成本。

**实战对应代码**：`projects/week1-quickstart/05_mini_rag.py` 就是完整的 RAG 最小实现，代码量 200 行，看懂了面试就能说清链路。

### Q3：LoRA 原理？为什么能有效？LoRA vs QLoRA vs 全参微调怎么选？
**满分答案框架**：
> 核心思想：预训练权重 W₀ 冻结，在旁边加低秩旁路 BA，前向 `h = W₀x + BAx`，只训练 A 和 B（r<<min(d,k)，参数少 100~1000 倍）。
>
> **为什么有效**：论文证明，下游任务的权重更新本质上在一个低秩子空间，低秩矩阵足够表达变化，不损失精度。训练初期 A 初始化为 0，B 高斯小方差，所以刚开始 BA=0，不影响原模型。
>
> **选型表**：
> | 方案 | 显存需求 | 效果 | 适用场景 |
> |------|----------|------|----------|
> | 全参 | 最高（7B fp16≈140GB） | 最好 | 大规模数据+多卡A100 |
> | LoRA | 中等（7B≈10-20GB） | 接近全参（95%+） | 绝大多数场景首选 |
> | QLoRA | 最低（7B≈5-8GB 可训，24GB可训70B） | 几乎和 LoRA 一致 | 消费级 GPU、大模型 |
>
> **推理**：可以 merge BA 到 W₀（零开销），也可以保留 adapter 插拔（多场景多 adapter 灵活）。

**追问必背**：
> Q：QLoRA 为什么 4bit 量化几乎不损失效果？
> A：用 NF4（Normalized Float 4bit）量化，适配预训练权重正态分布；双量化进一步压缩；训练时 paged optimizer 处理 OOM；量化误差被 LoRA 吸收，所以效果几乎和全精度 LoRA 一样。
>
> Q：为什么微调后效果反而掉了？可能有哪些原因？
> A：①数据质量差（低质/有毒/分布偏移大）；②学习率太大/太小；③过拟合（数据量小，epoch 太多）；④灾难性遗忘（没加通用数据）；⑤LoRA rank 选太大/太小；⑥数据格式不对（多轮对话格式错了）。

**实战对应项目**：W4/W5 做一个 QLoRA 微调垂直领域小模型，产出评测报告放简历上。

### Q4：DPO 和 RLHF 有什么区别？为什么 DPO 现在这么流行？
**满分答案框架**：
> RLHF 三阶段：SFT → 训练 Reward Model → PPO 优化。工程复杂，训练不稳定，需要单独训 RM，PPO 容易奖励黑客。
>
> DPO：直接偏好优化，跳过 RM，直接用「(chosen, rejected)」偏好对优化策略，数学上等价于 RLHF 最优解，训练简单稳定，不需要 RM，不需要 PPO。现在工业界做对齐都转 DPO 了。
>
> 如果你时间少，对齐直接走「SFT → DPO」两步就完了。

**追问**：ORPO 是什么？直接偏好优化在 SFT 阶段就做，更简单。

### Q5：Agent 和普通 ChatBot 本质区别是什么？Agent 核心组件？
**满分答案框架**：
- 普通 ChatBot：**只有文本生成**，输入问题 → 输出回答，不会用工具，不能感知环境，不能多步推理。
- Agent：**能自主行动完成任务**，核心五个组件：
  1. **大脑（LLM）**：做决策
  2. **规划**：分解任务、多步规划（CoT/ToT）
  3. **工具使用**：调用 API/数据库/搜索/code interpreter
  4. **记忆**：短期（上下文）/长期（向量库）/工作（scratchpad）
  5. **行动循环**：Thought → Action → Observation 循环直到完成（ReAct 范式）。

**追问必背**：
> Q：LangGraph 和传统 LangChain Agent 有什么区别？为什么现在 LangGraph 是主流？
> A：LangChain 传统 Agent 是黑盒循环，LMM 自己决定什么时候结束，不支持复杂分支、断点恢复、人工干预。LangGraph 用**显式状态机图**：节点是操作，边是状态转移，条件路由明确，内置 Checkpointer 自动持久化状态，支持中断/恢复/人工审批，多 Agent 协作清晰。我最近项目就是用 LangGraph 做 Supervisor-Worker 多 Agent，可控性强太多了。

### Q6：Agent 生产落地最大挑战是什么？怎么解决？
**满分答案框架（结构化答，分点说）**：

| 挑战 | 原因 | 解决方案 |
|------|------|----------|
| **非确定性** | LLM 可能格式错/幻觉/死循环 | 强制结构化输出+OutputParser 重试+最大步数限制+Guardrails |
| **延迟高** | 多步工具调用+长上下文+大模型推理 | 流式输出+并行工具调用+缓存（语义缓存+精确缓存）+模型路由（小模型答简单问题） |
| **成本高** | 多轮多步 token 累积 | 精简 Prompt+压缩上下文+模型路由+token 预算控制 |
| **可观测性差** | 多步执行出问题难排查 | LangSmith/Langfuse 全链路 Trace，每一步 prompt/工具结果/tokens 都记录 |
| **安全风险** | Prompt Injection → 让 Agent 执行危险操作 | 工具白名单+输入审查+敏感操作人工审批+数据脱敏 |
| **状态管理** | 长会话/多轮工具调用状态一致性 | LangGraph Checkpointer 持久化状态，thread_id 隔离 |

如果你是后端工程师，这里可以加分："我们后端做服务的思路很适合解决这些问题——高并发就是分层缓存、异步任务队列、熔断降级，和常规微服务一样的工程方法论套过来就行。"

### Q7：MCP（Model Context Protocol）是什么？为什么重要？
**满分答案框架**：
- MCP 是 Anthropic 提出的开放协议，统一大模型和外部工具/数据源的连接方式。
- 之前每个框架/每个工具都要定制适配，N 个 Client × M 个 Server 要 N×M 个适配。
- MCP 定义了 Tools/Resources/Prompts 三类原语，统一 Client-Server 架构（stdio/SSE 传输）。一个 MCP Server 可以被所有支持 MCP 的 Client（Claude Desktop/Cursor/Codex/LangGraph）直接使用，所以说像 USB-C 统一外设接口。
- 2026 年已经成为 Agent 工具接入的事实标准，我最近做的项目也接入了。

## 📝 AI Agent 面试答题总结

1. **先讲原理，再讲你做过的项目**：不要只说理论，一定要带自己做了什么，得到什么指标提升，面试官最爱听。
2. **后端优势放大**：讲部署/性能/可观测/安全的时候，把你后端经验套进去，这是你的差异化。
3. **最新动态要知道**：MCP、LangGraph、DPO、QLoRA 这些 2025-2026 主流技术要会说，说明你跟进前沿。
4. **不要硬编**：不会就说"这块我实践不多，但我的理解是...回去我再深入看一下"，诚实比瞎说强。### 🔹 基础概念三兄弟：Token / Temperature / Prompt（必背）

这三个是所有 AI 面试开场最基础的问题，必须1分钟讲清楚。

#### Token 是什么？
- **Token 是大模型处理文本的最小单位**，不是字，不是词，是一种通过 BPE（字节对编码）分词得到的"中间单位"
- 中文 1 字 ≈ 1.5-2 tokens，英文 1 单词 ≈ 1-1.5 tokens
- **为什么要关心 Token**：① 计费按 token 算（输入+输出分开）；② 上下文窗口限制（如 GPT-4o 128K ≈ 10万中文字）；③ 超长内容需要截断/摘要
- BPE 算法原理：先把文本拆成单字节，反复合并高频字节对，直到达到词表大小（如 GPT 词表约10万token）

#### Temperature 是什么？
- **控制回答的随机性/创造性**，取值 0~2
  - T=0：贪心选概率最高的词，每次回答几乎一致，确定性强 → 适合代码/事实问答/RAG场景（防幻觉）
  - T=0.7：默认值，平衡创意和靠谱 → 适合通用聊天
  - T=1.0：高随机性，创意强 → 适合文案/创意写作
  - T=1.5+：放飞自我，容易胡说 → 适合头脑风暴
- **技术原理**：softmax 前除以 T
  - T→0：概率分布变尖锐，高概率词概率更高 → 确定
  - T→大：概率分布变平，低概率词也有机会 → 随机
- **搭配使用**：通常和 Top-P（核采样，如 P=0.9）一起用，限制候选词范围，避免生成完全离谱的内容

#### Prompt 是什么？
- **Prompt = 给模型的全部输入**，通过 messages 数组分角色组织：
  - `system`：系统人设/规则，整个对话生效（"你是直播电商助手，禁止编造价格"）
  - `user`：用户问题
  - `assistant`：AI 历史回答（多轮记忆）
- **好 System Prompt 的 5 要素**：①角色 ②任务 ③约束（不能做什么）④格式要求 ⑤示例（Few-shot）
- **Prompt 为什么重要**：同一个模型，好 Prompt 和差 Prompt 回答质量差10倍；调 Prompt 比微调快、便宜、随时改，是 AI 工程师最高频工作

## 三、Agent 记忆机制（面试必问，95分答案）

> 参考：小林《图解Claude Code · 记忆机制图解：为什么不用向量数据库？》
> https://xiaolinnote.com/claudecode/source/cc_memory.html
### Q0：概念铺垫（先懂这三件事再进记忆机制）

**① 短期记忆 vs 长期记忆（最基础，答错全盘崩）**

| 维度 | 短期记忆 | 长期记忆 |
|---|---|---|
| 本质 | 当前任务的上下文（工作台） | 跨任务的经验库（笔记本） |
| 存在哪 | 每次请求的输入里，不用检索 | 外部存储：向量库/SQLite/MD 文件 |
| 生命周期 | 任务结束就清空 | 持久保存，跨对话 |
| 什么时候读 | 任务中随写随读（免检索、实时） | 任务前检索注入（top-k） |
| 什么时候写 | 任务中实时记中间状态 | 任务后沉淀可复用的经验 |
| 作用是 | 防"中途失忆" | 防"每次都是新手" |

- 一句话：**短期记忆 = 喂给模型的那批文字；长期记忆 = 存在模型外面、要用时再取出来喂的文字**。.md / SQLite / 向量库都是长期记忆的存储介质；短期记忆就是上下文本身（conversation.jsonl 只是日志，不是记忆机制）。
- 任务生命周期三阶段：**任务前=长期检索注入（带经验开场）；任务中=短期工作台（防失忆）；任务后=短期清空+长期沉淀（跨任务积累）**。用错层：长期当工作台=慢+拿到旧快照失忆；短期不清空=污染+爆 context。

**② LLM 怎么"记住"过去聊天（5 层机制，从简到繁）**
1. 全量重放：每次请求带全部历史（网页聊天默认）→ 超长报 Input length exceeds max（真实踩过）
2. 滑动窗口：只留最近 N 轮 → 永不超限但早期关键信息丢
3. 摘要压缩：旧对话压成几句话替换原文 → 丢细节、摘要也膨胀（/compact）
4. 关键信息外置：结论写文件（CURRENT_PROGRESS.md/CLAUDE.md），新对话读文件代替回忆（本学习仓库=此方案）
5. 向量检索：历史落库+向量化，按需召回 top-k 注入
- 面试答法："LLM 无状态，记住过去=要么把历史喂给它（短期），要么存在外面、需要时取出来喂（长期）；核心矛盾是把什么放进有限的上下文。"

**③ 怎么让 LLM 反思（4 个工程抓手）**
1. Prompt 硬约束：System Prompt 写死"每完成一个任务必须按模板输出反思"
2. 结构化模板（Reflexion 三问）：目标是什么 / 哪里不对（要证据，不许说"没做错"） / 下次怎么做（可复用教训，答不出具体做法=无效反思）
3. 触发时机：失败后必反思、任务收尾反思；评估不过关→反思→修正→重试（≤N 次）——反思=一次额外调用，别全程开
4. 落库沉淀：教训带 {type, reflection, created_at} 进错题本，下次同类任务前注入（不落库=白反思）
- 区分：**总结=压缩信息（一条 prompt）；反思=评估自己+沉淀改进（需要 触发→模板→落库→注入 闭环）**。用户自建 skill（task-status-report/git-verify-push）= 反思工程化。


### Q1：LLM 是无状态的，那记忆到底存在哪？

- LLM 本身**没有任何记忆**，每次对话都是独立的。所谓"记得你"，靠的是外部机制把历史再喂给它。
- 记忆机制的本质 = **在工位上贴便签**。核心问题只有三个：**贴在哪（存储）、谁来贴（写入端）、什么时候撕（老化）**。
- 一句话开场："LLM 是无状态的，记忆机制的三个核心问题是贴在哪、谁来贴、什么时候撕。"

### Q2：业界主流方案对比，共同病根是什么？

| 方案 | 思路 | 问题 |
|---|---|---|
| 滑动窗口 | 只保留最近 N 轮 | 早期关键信息丢失 |
| 对话摘要 | 定期把历史压缩成摘要 | 摘要损失细节、摘要本身也会膨胀 |
| 向量检索 | 全文 embedding，相似度召回 | 见下面四病根 |
| 分层存储（MemGPT/Letta） | core/recall/archival 三层，LLM 当操作系统搬数据 | 概念多、迁移成本高，底层还是 embedding |

**四类方案共同病根（背下来）**：
1. **自由文本无约束**：存什么没规则 → 记忆库迅速膨胀成垃圾堆
2. **不区分类型**：用户画像/项目动态/外部指针一锅炖 → 哪个都查不准
3. **没有老化机制**：存进去就永久，"项目用 Kong"半年后换 nginx，旧记忆还在说 Kong → **"权威的错误"比没记忆更糟**
4. **重检索、轻写入**：全在优化"怎么查到"，"该不该存"放任不管 → 垃圾进、垃圾出

### Q3：Claude Code 怎么做（反直觉：不用向量数据库）

**两层记忆架构**：
- **静态层 = CLAUDE.md（声明式）**：项目记忆，人写的规则。分 6 个层级（CLAUDE.md → .claude/ 子目录 → 按路径/类型按需加载）。加载时比对当前编辑文件路径，**只有匹配的规则才拼进 system prompt** → 大项目几十条规则也不爆上下文。
- **动态层 = 自动记忆系统（学习式）**：agent 自己学、自己写、自己用。

**记忆系统的关键设计**：
1. **MEMORY.md 索引常驻 + 正文按需加载**：目录里一个 MEMORY.md 是所有记忆的索引（name + description 一句话），**只把索引塞进 system prompt，正文按需加载**——像工具书，先看目录，需要哪章翻哪页。
2. **记忆强制四种类型**：`user`（你是谁）/ `feedback`（你的偏好，正文必须带 Why + How to apply）/ `project`（项目动态，相对日期转绝对日期）/ `reference`（去哪查什么的外部指针）→ 存之前先想清楚是哪一类，信息形态有纪律。
3. **"不该存"清单**：代码模式/架构/文件路径（grep 就能拿到）、git 历史（git log 是权威）、调试方案（fix 已在代码里）、CLAUDE.md 已有内容、临时任务状态 → **只记代码推不出来的东西**。
4. **小模型做选择题**：用便宜模型（Sonnet）当选择器，从索引里选 top-5，过滤已露脸的 + 过滤工具文档。
5. **老化警告**：2 天前的记忆主动加 stale 提醒，逼模型先验证再使用——治"权威的错误"。
6. **索引双截断防炸弹**：`MAX_ENTRYPOINT_LINES = 200`、`MAX_ENTRYPOINT_BYTES = 25_000`，任一触发就截断并告诉模型"索引被截过"。（真实案例：197KB 的索引只有不到 200 行——光看行数会漏）

### Q4：新版 Claude Code Memory 工具：SQLite 里存的是什么？

**你的问题"存的是向量和具体 text 吗"——是的，两样都存。**
- 旧版/小林文章讲的是 markdown 方案；**新版 Memory 工具用 SQLite 数据库**（`~/.claude/memories/<项目>/memories.db`）：
  - **text 原文**：记忆内容 + 元数据（type、created_at、updated_at、last_accessed 等）
  - **向量 embedding**：每条记忆的语义向量（几百维浮点数组，存 BLOB），用于相似度检索
- 检索流程：新对话 → 当前查询转成向量 → SQLite 里做**向量相似度检索**（sqlite-vec 扩展/暴力扫描）→ 取 top-k → 把**命中的原文 text 注入上下文**。
- **关键认知：LLM 看到的是 text，不是向量。向量只用来"找"，text 用来"用"。**

### Q5：SQLite 也膨胀了怎么办？（本题精华）

**第一层认知：存储膨胀 ≠ 上下文膨胀。**
- SQLite 存 10 万条记忆，磁盘变大、检索变慢——但这**不会直接伤害 LLM**，因为每次只取 **top-k（5~10 条）**注入上下文。
- 真正危险的是**常驻上下文**的东西膨胀：Claude Code 里常驻的是 MEMORY.md 索引，所以才有 200 行/25KB 双截断 + 按需加载。
- 面试金句："记忆系统的核心矛盾是'该把什么放进有限的上下文'，而不是'存储能放多大'。存储可以无限，上下文有限。"

**第二层：存储膨胀本身的治理手段（可迁移到自己项目）**：
1. **只取 top-k**：检索命中 5~10 条，DB 再大也不爆上下文
2. **老化机制**：记忆带时间戳，超过阈值（如 2 天）标记 stale，让模型验证后更新/删除——治"权威的错误"
3. **合并/摘要**：相似记忆定期合并成一条（呼应 Compact 压缩思路）；旧记忆聚合为归档摘要
4. **按项目分库**：避免单库无限膨胀（Claude Code 就是按项目分目录/分库）
5. **向量索引**：HNSW/IVF 索引避免全表扫描；SQLite 可用 sqlite-vec 扩展
6. **写入端控制**：MEMORY.md 的"不该存清单"从源头防垃圾进（存得少，膨胀就慢）

### Q6：面试怎么答记忆机制？（答题模板）

**60 分**：上向量数据库，存 embedding，相似度检索。
**95 分**（按顺序说）：
1. 先指出 **LLM 无状态**，记忆的本质是"贴便签"，核心是"贴在哪、谁来贴、什么时候撕"
2. 指出业界四类方案（滑动窗口/摘要/向量检索/分层存储）的共同病根：**无约束、不分类、无老化、重检索轻写入**
3. 举 Claude Code 反例：**结构化文件 + LLM 选择**，不用向量库
   - 两层架构：CLAUDE.md 声明式 + 记忆系统学习式
   - 四种类型强制分类；MEMORY.md 索引常驻、内容按需加载
   - 小模型选 top-5；2 天 stale 老化提醒
   - 新版 SQLite + embedding：存 text + 向量，top-k 注入
4. 给可迁移原则：**结构化优于自由文本、索引常驻+内容按需、廉价模型做选择题、时间感知+主动验证**
5. 收尾金句："核心矛盾是'把什么放进有限的上下文'，存储可以无限，上下文有限"


### Q7：每次对话都会全量输入 memory.md 吗？（不会，分层按需）

**不会全量**，否则 50 条 × 200 字 = 1 万字几千 token，system prompt 直接被撑爆（小林原文原话）。实际是三层设计：

1. **索引常驻**：MEMORY.md 里每条记忆只有一句话（name + description），始终在 system prompt 里，且有**双截断保护**（200 行 / 25KB）。
2. **正文按需**：模型看到索引后，只有被选中的记忆才读正文——小模型选择器选 top-5 / 按路径匹配，命中才加载。
3. **SQLite 版按需（新版 Memory 工具）**：记忆全在 SQLite 里，**模型主动调用 Memory 工具的 recall/search**，检索 top-k 注入工具结果——不是被动全量喂。

类比：工具书——不背整本书，看目录，需要哪章翻哪页。**注入是"模型决定要不要查 + 查到什么"**，不是"每次都全量塞"。

### Q8：SQLite 向量检索具体怎么实现？（工程细节）

**存储 schema（典型实现）**：
```sql
CREATE TABLE memories (
  id INTEGER PRIMARY KEY,
  content TEXT,          -- 原文 text
  type TEXT,             -- user/feedback/project/reference
  created_at TEXT,
  updated_at TEXT
);
CREATE TABLE memory_embeddings (
  memory_id INTEGER PRIMARY KEY,   -- 与 memories.id 关联
  embedding BLOB,                  -- 768 个 float32（维度取决于 embedding 模型）
  FOREIGN KEY (memory_id) REFERENCES memories(id)
);
```

**写入**：新记忆 → 先存 text（memories 表）→ embedding 模型生成向量 → 存 memory_embeddings（同一条记忆一个 id 关联）。

**检索三种实现**：
1. **暴力扫描**（数据量小，几千条内）：全表把 embedding 读出来，应用层算余弦相似度，排序取 top-k。简单，纯 SQLite 自带能力，几千条全扫也就毫秒级。
2. **sqlite-vec 扩展**（SQLite 生态的向量搜索扩展，类似 sqlite-vss）：
```sql
CREATE VIRTUAL TABLE vec_memories USING vec0(embedding float[768]);
INSERT INTO vec_memories(rowid, embedding) VALUES (1, ?);   -- 写向量

SELECT rowid, distance FROM vec_memories
WHERE embedding MATCH ?          -- ? 是查询向量
AND k = 10;                      -- 取最近 10 条
```
3. **外部向量库**：SQLite 只存 text，向量存 Milvus / Chroma / PGVector，两边用 id 关联——数据量大时的分布式方案。

**相似度计算**：余弦相似度 = 点积 / (|a|·|b|)；向量归一化后，点积 = 余弦。距离越小越相似。

**检索后处理（关键）**：top-k 只是"候选"，还要做相似度阈值过滤（低于阈值视为无关，不注入，防污染）、去重、按新鲜度排序，最后**只把 text 注入上下文，向量永远不进上下文**。

**Claude Code 实际实现**：闭源。公开信息是"SQLite + semantic search（embedding 语义检索）"，具体走 sqlite-vec 还是自定义实现不公开——面试说"SQLite 存 text+向量，top-k 语义检索注入"即可，能画出上面的 schema 和检索流程就是加分。


### Q9：每次对话，哪些 md 全量加载、哪些部分加载、怎么选择？

**原则一句话：凡是进 system prompt 的都是"索引/描述"级别（小），正文一律按需。**

**全量加载（每次对话都进 system prompt）**：
1. **系统提示词 + 工具定义**：模型人设、行为规则、可用工具 schema（这是必须的）
2. **CLAUDE.md 六层（声明式记忆，叠加不覆盖）**：
   - Managed（系统级，管理员才能改，公司强制策略）
   - User（~/.claude/CLAUDE.md，全局个人偏好，所有项目生效）
   - Project（项目根 CLAUDE.md / .claude/CLAUDE.md，签入 git 团队共享）
   - Local（CLAUDE.local.md，不签 git 个人用）
   - Auto（AutoMem，Claude Code 自动写的项目记忆）
   - Team（Auto 目录下 team/ 子目录，团队共享 AI 学的偏好）
   - 六层启动时**全部拼接**进 system prompt（叠加不覆盖）；支持 `@include` 引用其他文件（类似 C 的 #include）
3. **MEMORY.md 索引**：每条记忆一句话（name + description），常驻，但**双截断保护**（200 行 / 25KB）
4. **Skills 清单**：所有 skill 的"名称 + 描述"（索引级），正文不加载

**部分加载（按需，不进常驻）**：
1. CLAUDE.md 里带 `paths` 的规则正文 → 路径匹配才注入
2. 记忆正文（每条独立 md）→ 小模型选择器选 top-5 才读
3. Skill 正文（SKILL.md 完整内容）→ 模型判断相关才加载
4. Subagent 定义 / MCP 工具文档 → 用到才加载
5. SQLite 记忆 → 模型主动调 recall/search 工具，top-k 注入

**部分加载的四种选择机制**：
1. **路径 glob 匹配**（规则层）：规则 frontmatter 带 `paths: ["**/*.tsx", "**/*.jsx"]`，加载时比对当前编辑文件路径，命中才拼进 system prompt——让大项目几十条规则只在需要时占 token
2. **主模型意图判断**（Skill 层）：模型根据用户请求 + skill 描述，决定调用哪个 skill，调用时才加载正文
3. **小模型选择器**（记忆层）：用便宜模型（Sonnet）从 MEMORY.md 索引选 top-5，且做两个过滤：recentMemories（已露脸的不重复挑）+ recentTools（正在用的工具，其文档不塞）
4. **工具调用**（SQLite 层）：模型主动调 recall/search，检索 top-k + 阈值过滤

**注入方式（细节加分）**：选中的记忆**不拼 user message**（怕模型当成用户刚说的话），而是用 `<system-reminder>` 标签包裹注入，并带老化警告：
```
<system-reminder>
This memory was saved 5 days ago. Verify it's still accurate before acting on it.
[记忆内容]
</system-reminder>
```
今天/昨天的记忆不警告；**2 天前的主动加"这是历史快照"警告**，逼模型带验证心态去用——治"权威的错误"。

**截断兜底**：所有常驻文件都有大小上限，超了截断并明确告诉模型"索引被截过，有内容没加载"，让模型自己心里有数。


### Q10：记忆机制一张图（目录 vs 正文，全量 vs 按需）

**核心心智模型：Agent 的记忆 = "图书馆"。目录全量装进脑子，正文按需去书架拿。**

**每次对话，模型"看到"的（全量加载，都是小东西）**：
```
┌────────────────────────────────────────────────────┐
│ system prompt（全量、每次都在）                        │
│ ① 系统提示词：人设/行为规则/工具 schema                │
│ ② CLAUDE.md 六层规则正文（人写的项目规则，量小所以全量）  │
│ ③ MEMORY.md 索引：记忆的"目录"，每行一条记忆的一句话      │
│ ④ Skills 清单：skill 的"目录"（name + description）     │
└────────────────────────────────────────────────────┘
```

**模型"需要时才去拿"的（按需加载，都是大/低频东西）**：
```
┌────────────────────────────────────────────────────┐
│ ① 记忆正文：某条记忆的完整内容（从 SQLite 检索 top-k）  │
│ ② SKILL.md 全文：规则/用法（模型判断相关才加载）        │
│ ③ Subagent 定义 / MCP 工具文档：用到才加载             │
└────────────────────────────────────────────────────┘
```

**真实例子（你机器上的 SKILL.md 就是这套结构）**：
```markdown
---
name: truncate-long-output          ← 这行 = "目录行"（全量加载）
description: 自动截断长工具输出...    ← 这行 = "目录行"（全量加载）
---
# 长输出自动截断 Skill               ← 下面是"正文"（按需加载）
## 规则
1. 所有命令工具输出都要截断...
```
每次对话我只看到所有 skill 的 name+description 清单；真要遵守规则时才读某个 SKILL.md 全文。

**memory（md）与 SQLite 的分工：md = 可见目录，SQLite = 检索仓库**

```
存储层（长期记忆的仓库）           可见层（模型的"目录"）
┌──────────────────────┐       ┌──────────────────────┐
│ SQLite memories.db   │       │ MEMORY.md            │
│  memories 表          │  生成  │  name + description  │
│   正文 text + 元数据   │ ─────► │  每行一条（一句话）    │
│  embeddings 表        │  同步  │  全量进 system prompt│
│   向量（语义检索用）    │ ◄───── │  200行/25KB 截断保护  │
└──────────────────────┘       └──────────────────────┘
```

- **写长期记忆**：对话中发现值得记的 → agent 判断类型（user/feedback/project/reference）→ 正文+向量写进 SQLite → 同步更新 MEMORY.md 目录（新增一行）
- **读长期记忆**：每次对话 MEMORY.md 目录全量进 system prompt（模型知道"有哪些记忆"）→ 模型觉得某条有用 → 调 recall 工具 → SQLite 向量检索 top-k → 命中的正文 text 注入当前对话
- **为什么这样分**：md 小、常驻、人可读、可 git 管理（团队共享）；SQLite 大、按需、可语义检索（机器友好）。**目录管"知道有什么"，仓库管"能取到什么"**。

> 演进说明：小林文章讲的旧版 = 正文也存 md 文件（每条一个），检索靠小模型选择器；新版 = 正文+向量存 SQLite，检索靠 embedding。**两版核心不变：索引常驻 + 正文按需。**


### Q11：MEMORY.md 存的是什么？短期记忆还是 SQLite 的索引？

**MEMORY.md = 长期记忆的索引（目录）。既不是短期记忆，也不是 SQLite 本身。**

**记忆三层模型（面试直接画这个图）**：
```
① 短期记忆（会话内）：当前对话上下文
   = system prompt + 最近 N 轮 + 工具结果
   管理：滑动窗口 + Compact 压缩（太长→压成摘要）
   会话结束只留 jsonl 存档，不跨会话
② 长期记忆（跨会话）
   ├── 目录层：MEMORY.md（常驻 system prompt）
   │     每行 = 一条记忆的 name + description（一句话）
   │     200行/25KB 双截断保护
   └── 仓库层：SQLite（正文 text + 向量）或旧版独立 md 文件
         按需检索 top-k，命中才注入正文
```

**一条记忆的旅程（分清每层放什么）**：
```
用户说"回复不用总结，diff 即可"
  → 写入长期记忆：
    ① SQLite 仓库：content 全文 + type=feedback + 时间戳 + embedding 向量
    ② MEMORY.md 目录：新增一行 "feedback: 回复不总结，diff 即可"
下次对话：
    ③ MEMORY.md 目录全量进 system prompt（模型知道有这条，但没见正文）
    ④ 模型调 recall → SQLite 向量检索 top-k → 命中 → 正文注入
```

**一句话**：MEMORY.md 管"模型知道有什么"，SQLite 管"模型能取到什么"；短期记忆是另一套东西（当前对话本身，会话内）。

### 项目映射（我们《直播电商智能助手》）

- C 端智能客服：用户画像/偏好用 **feedback 型记忆**（带 Why + How to apply），高频问题沉淀到 FAQ 缓存（对应 CLAUDE.md 静态层）。
- OnCall 助手：排障经验存 **reference 型记忆**（去哪查：Argos/监控面板/接口文档），不存具体代码（代码会变，存了就是"权威的错误"）。
- 记忆膨胀治理直接抄 Claude Code：索引常驻 + 正文按需、2 天 stale 老化、top-k 注入、按项目分库——这些设计决策都能经得起面试官深挖。

## 四、GraphRAG（面试必问）

> 参考：小林《图解Agent · GraphRAG 与 LightRAG》
> https://xiaolinnote.com/agent/rag/graphrag-lightrag.html

### Q1：Local Search"定位入口实体"的相似度搜索怎么推进？（所有实体节点怎么搜）

**破除直觉：不是真的一次性比对所有实体节点，而是 ANN（近似最近邻），把"全量"降成"局部"。**

**微观层：实体怎么变成向量、怎么比**
- 索引阶段：实体摘要（Summarization 产物）→ embedding 模型 → 每个实体一条向量 → 存入向量库并建索引
- 查询阶段：问题 → 同一个 embedding 模型 → 问题向量 → 与实体向量算相似度（余弦/内积）→ top-k

**宏观层：N 个节点怎么搜（面试背表格）**

| 方案 | 做法 | 复杂度 |
|---|---|---|
| 暴力法 | 与 N 个向量逐个算内积再排序 | O(N)，万级能忍，百万级每次几十~上百 ms |
| IVF（倒排文件） | k-means 聚成 K 个簇，只 probe 最近的 nprobe 个簇，簇内小范围精算 | O(N/K × nprobe) |
| HNSW（分层小世界图） | 多层图：上层稀疏快速定位区域，下层稠密精搜，顶层入口贪心下降 | O(log N) 跳，FAISS/Milvus 最常用 |
| PQ（乘积量化） | 高维向量切段、码本量化成短码，距离在短码上算，省内存省算力 | 常配合 IVF/HNSW |

实际效果：10 万实体建 HNSW 后，单次查询从 10 万次内积降到"每层几十候选 × log 层数"，亚毫秒~毫秒级。

**GraphRAG Local Search 完整链路（两步分开）**：
```
索引阶段（离线一次）：实体摘要 → embedding → 向量库建 ANN 索引
查询阶段（在线每次）：
  ① 问题 → embedding → 问题向量
  ② 向量库 ANN 检索 → top-k 最相似实体（入口实体）   ← 图外向量检索
  ③ 从入口实体沿图的边扩展 1~2 跳
     = 邻居实体 + 关系 + 原始文本块 + 所属社区报告    ← 图上游走
  ④ 组装上下文 → 喂 LLM 生成答案
```
- ② 是"图外的向量检索"，不知道图结构也能搜，就是普通 ANN；③ 才是"图上的遍历"，顺着边跑。向量库只管找入口，图遍历由图存储负责。
- **面试金句**：普通 RAG 检索"相似的文本块"，GraphRAG 检索"相似的实体 + 它的整个关系网"——入口定位靠 ANN，扩展靠图遍历。
- 对比：LightRAG 省掉社区层（Leiden/社区摘要），入口实体定位 + 一跳邻居，本质同一套 ANN + 浅图遍历，所以查询延迟低一个数量级。
- **项目映射（直播电商智能助手）**：实体 = 商品/秒杀活动/竞拍场/库存状态/用户身份。问"秒杀活动A显示有货却拍不了" → ANN 定位「秒杀活动A」→ 沿边扩到「库存扣减服务/Redis缓存/扣减流水/商品卡展示」→ 关系链组装进上下文。面试答："入口用向量库 ANN（HNSW）定位，扩展用图遍历，检索毫秒级，瓶颈只在 LLM 生成。"

### Q2：k-means 是什么？HNSW 怎么构建、怎么搜索？（ANN 底层原理）

#### k-means（无监督聚类，IVF 的"建目录"工具）

**目标**：把 N 个点分成 K 个簇，让"每个点到所属簇中心距离平方和"最小（簇内最紧凑）。

**流程（迭代到收敛）**：
```
① 初始化：随机选 K 个点当簇中心（centroid）
② 分配：每个点分给离它最近的簇中心
③ 更新：簇新中心 = 该簇所有点的平均值
④ 重复②③直到中心不再变化 → 收敛
```
1 维例子（K=2），点 1,2,8,9,10,20：
```
初始中心 2 和 10
第1轮分配：{1,2}归2，{8,9,10,20}归10
第1轮更新：A=(1+2)/2=1.5，B=(8+9+10+20)/4=11.75
第2轮分配/更新无变化 → 收敛，得 {1,2} 和 {8,9,10,20}
```
复杂度 O(N×K×d×迭代)。**在 ANN 里的角色**：建索引时用 k-means 把向量聚成 K 个簇（Voronoi 单元格），查询时问题向量只进最近的 nprobe 个簇内精确搜 → 全量 N 变局部 N/K。k-means 本身不是检索，是 IVF 的目录。

#### HNSW（分层小世界图）

**直觉**：陌生城市找店——高速（长跳）→ 主干道 → 小巷。层越高路越少、跳得越远；第0层稠密、含所有节点和精确邻居边。
```
Layer 2:  ●──●──●
Layer 1:  ●──●──●──●──●
Layer 0:  ●●●●●●●●●●●●   ← 所有节点 + 精确邻居关系
```

**构建（插入一个新向量）**：
```
① 升层：从第0层起每层以概率 mL 升层（高层 = 低层的抽样，越往上节点越少）
② 每层贪心搜索：从该层入口走到"层内离目标最近的点"，直到走不动
③ 降到下一层重复，直到第0层 → 得到候选近邻
④ 第0层插入：连前 M 个最近邻居，用"邻居选择启发式"修剪
   （只保留覆盖不同方向的邻居，防止边全指同一区域）
⑤ 若抽到更高层，同样在高层建边
```
参数：`M`（每点最大连接数）、`efConstruction`（建索引候选列表大小）、`mL`（升层概率）。

**搜索（找 top-k）**：
```
① 从最高层入口点出发
② 每层贪心下降：反复跳到"比当前点更接近 query"的邻居，直到局部最优点
③ 降一层重复 → 每层把位置校准到更精确区域
④ 第0层改为光束搜索：优先队列按距离排序，弹出最近点扩张其邻居，
   记录全局 top-k，直到队列最近点不比 top-k 更近 → 停止
⑤ 返回 top-k = 入口实体
```
复杂度：每层 O(M) 次距离计算 × O(log N) 层 → 10 万向量亚毫秒~毫秒。

**为什么 HNSW 是 FAISS/Milvus 主力（面试一句）**：无需训练（对比 IVF 要先跑 k-means）、精度高查询快（NSW 保证长跳捷径，分层把长跳变成逐层逼近）。缺点：内存占用高（每点多层邻居边）。

### Q3：HNSW 搜索细节——从哪个点开始比？怎么找相近点？怎么算本层结束？

**① 起点**：全局入口点（entry point，构建时指定，如 0 号节点）只在**最高层**用；之后每降一层，**起点 = 上一层贪心走到的落脚点**（带下去）。

**② 怎么找相近点**：不扫全图，只看**当前节点的直接邻居**（每层每条边在构建时定死，存成邻居 ID 列表）。拿 query 向量和邻居向量逐个算距离（欧氏/余弦），**选离 query 最近的邻居走过去**——贪心 = 每步只挑眼前最好的方向。

**③ 本层何时结束**：走到 c 后，若 **c 的所有直接邻居都不比 c 更接近 query**（c 是"自己+邻居"里最近的），c 就是本层局部最优点 → 本层结束，带 c 降一层。

**1D 例子（query=12，点 0,5,10,15,20）**：
```
Layer 2:  0 ──────── 20       Layer 1:  0 ── 10 ── 20       Layer 0:  0─5─10─15─20
从入口 0 开始：dist(0,12)=12 > dist(20,12)=8 → 走到 20
在 20：邻居只有 0，没有更近 → 本层结束，落脚 20

Layer 1 起点=20：dist(20,12)=8 > dist(10,12)=2 → 走到 10
在 10：邻居 0、20 都不比 10 近 → 本层结束，落脚 10

Layer 0 起点=10：改光束搜索（beam search）
  维护按距离排序的候选队列：弹出最近点 → 扩张其邻居 → 记录全局 top-k
  直到队列最近点不比 top-k 更近 → 停止，返回 top-k（如 10、15）
```

**面试细节**：
- 贪心 = 离散版"爬山"：每步只看当前节点邻居（度 ≈ M），不看全图 → 每步 O(M)，层数 O(log N)，总 O(M·log N)
- 为什么不会掉进远方错误局部最优：高层是**长跳**（一步跨很远先到大致区域），低层才精搜——分层存在的意义就是"先粗定位再细校准"
- 高层用单线贪心（ef=1，快，只要大致区域）；**第0层用光束搜索**（efSearch≈50~200 候选池，防局部最优、保证 top-k 质量）
- 插入节点与查询共用同一套入口贪心逻辑：从顶层入口往下走到第0层，找候选邻居建边

### Q3-追问：ef 是什么？（HNSW 查询参数，实测语句必问）

- **ef = exploration factor（探索因子）**：HNSW **查询时**的参数 = 搜索过程中一直维护的候选节点队列上限（"同时盯着多少个候选点找"）
- **机制**：第 0 层精搜阶段维护容量上限 ef 的候选队列（按距离排序）→ 循环：弹出最近点 → 扩张邻居 → 更近的塞回（放不下丢最远）→ 直到队列最近点不比第 k 近更近 → 停止返回 top-k
- **ef 越大** → 搜索路径越宽 → 召回越高但越慢；**ef 越小** → 快但可能掉进局部最优；**硬性约束 ef ≥ k**
- **HNSW 三参数分工（面试必分清）**：
  | 参数 | 时机 | 控制什么 | 典型值 |
  |---|---|---|---|
  | M | 建图 | 每节点最大连接数（定结构） | 16~64 |
  | efConstruction | 建图 | 建图时候选池（定质量） | 100~500 |
  | ef/efSearch | 查询 | 查询时候选池（定召回） | 10~500 |
  - M 建图定死结构，ef 查询时定"沿结构搜多宽" → **ef 是线上唯一不动索引就能调召回/延迟的旋钮**
- **读实测语句**："HNSW 在内存、ef=100" = 索引全在 RAM（无磁盘 IO，纯 CPU 性能）+ 候选池宽度 100（召回/延迟常用平衡点，FAISS/Milvus 默认量级）；要高召回提 200~500，要高 QPS 降到 10~50
- 面试一句话："ef 是查询时的探索因子=候选池容量上限，池越大搜索越宽、召回越高但越慢；M 定结构、efConstruction 定建图质量、ef 定查询召回，ef 必须 ≥ k，100 是常见平衡点。"

### Q3-追问2：M 参数"每点连几条边"啥意思？每层查询过程是什么？（追问）

**① M 参数 = 每个节点每层最多连接的邻居数（出度上限），不是"图共几个节点"**
- 默认值：HNSW 论文 16；FAISS 常用 HNSW32（M=32）；Milvus 默认 4、建议 8~64 → 面试说"常用 16~32 量级"
- **第 0 层特殊：上限 2M**（maxM0=2M，所有节点都在第 0 层，要更稠密保连通+精搜质量）
- 实际建边数通常 M/2~M：建图用"邻居选择启发式"修剪，只留**覆盖不同方向**的邻居，防止边全指同一区域
- 调参影响：M 大 → 图稠密 → 召回高但每步慢+内存大（每条边存邻居 ID）；M 小 → 稀疏 → 快省内存、召回可能降
- 一句话："M 决定图稠密度，是建图时的召回/速度/内存旋钮（查询时旋钮是 ef，别混）"

**② 每层查询过程（从顶层一路降到第 0 层）**
- 每层动作一样：从起点出发，看当前节点直接邻居谁离 query 更近就走过去，**走到走不动（自己比所有邻居近）= 本层局部最优 → 结束**；区别在起点和搜索宽度
- 过程：
  ```
  Layer 2（最稀疏）: 起点=全局入口 → 单线贪心长跳，只要大致区域 → 落脚 ↓
  Layer 1（中层）  : 起点=上层落脚 → 贪心校准到更精确区域 → 落脚 ↓
  Layer 0（最稠密）: 起点=上层落脚 → 光束搜索（ef 候选池）弹最近点扩张邻居，
                     直到候选池最近点不比第 k 近更近 → 返回 top-k
  ```
- 设计动机：高层=高速路（一跳跨半个图确认区域），低层=小巷子（区域内精搜）——**先粗定位、再细校准**；只在第 0 层傻搜 = 遍历稠密图，慢死
- 复杂度：每层 O(M) 距离计算 × O(log N) 层 = 总 O(M·log N)

### Q3-追问3：怎么计算"当前节点离哪个邻居最近"？（HNSW 查询核心步骤）

- **不是图论跳数距离，是向量空间度量**：邻居就是一条向量，拿 query 和它们逐个算数学距离取最小
- **三种度量（建库时定 METRIC_TYPE）**：L2 欧氏 √Σ(aᵢ-bᵢ)²（越小越近）；余弦 (a·b)/(|a||b|)（越大越相似，转 1-cos 当距离）；内积 a·b（越大越相关）
- **计算过程（伪代码）**：
  ```
  for n in neighbors[c]:              # 最多 M 个，构建时定死
      d = distance(q, vec[n])         # L2 就是 Σ(qᵢ-vᵢ)² 再开方
      取 d 最小者为 best → 走过去
  若 min_dist > distance(q, vec[c]) → 自己比所有邻居近 → 走不动，本层结束
  ```
- **关键：比较的是"邻居们谁离 query 近"，不是"邻居离当前节点近"**——每步都朝 query 方向挪
- 例子：q=(0.2,0.8)，邻居 n1=(0.1,0.9)/n2=(0.9,0.1)/n3=(0.3,0.5) → L2 分别≈0.141/0.990/0.316 → 走 n1；768 维同理，只是平方和从 2 项变 768 项（维度变原理不变）
- **成本与优化**：每步 O(M×d) 浮点运算；向量+邻居列表在内存，多核 SIMD/并行算 M 个距离再归并取最小 → 压测 QPS 的关键
- 面试一句话："邻居就是 M 条向量，拿 query 逐个算度量距离取最小者走过去；自己比所有邻居近就本层结束。每步 O(M·d)，内存向量+多核 SIMD 并行。"

### Q3-追问4：query A 从哪开始比？跟所有向量都比一遍吗？（追问）

- **否，绝不和所有向量比**——这是 HNSW 存在的意义。只跟"当前节点的直接邻居"（≤M 个）比
- **起点 = 全局入口点 entry point（构建时指定，如 0 号节点），只在最顶层用**；之后每层起点 = 上层落脚点
- **顶层走查（10 万节点示例）**：顶层只有几百个节点（抽样）→ 算 A 与入口点+它几个邻居的距离（个位数次）→ 走最近的 → 贪心到局部最优 → 降层；每层约 M=16 次/步 × 3 步 × 5 层 ≈ 200~300 次距离，不是 10 万次
- **"第一层"歧义澄清**：最顶层=入口贪心（比几个邻居）；第 0 层=光束搜索（ef 候选池内扩张，依然不是全库，只是沿图走到的局部区域）
- **为什么入口点可能离 A 很远也不怕**：高层长跳结构，贪心几步就到 A 所在片区，低层再精搜——靠长跳快速逼近
- 对比：KNN 暴力 = N 次全比；HNSW = O(M·log N) 次（每步 O(M)，M=邻居上限）
- 面试一句话："A 从全局入口点开始，每层只跟当前节点的直接邻居（≤M 个）比距离贪心走，每层起点是上层落脚点；顶层入口唯一、第 0 层光束搜索走候选池——从不全量比对，所以 10 万向量只算 O(M·log N) 次距离。"

### Q3-追问5：两层 HNSW 完整走查例子（含全部距离计算）

**图的设定（1D 坐标，Q=27，返回 top-2）**：
```
坐标：  0   5   8  12  15  20  25  30  35  40  45
节点：  A   B   C   D   E   F   G   H   I   J   K
Layer 1：A(0)──F(20)──K(45)（长跳）
Layer 0：A─B─C─D─E─F─G─H─I─J─K（近邻链，所有节点）
```

**顶层（Layer 1）贪心下降（3 次距离）**：
```
起点=入口 A：dist(Q,A)=27，dist(Q,F)=7 → 走到 F
在 F：邻居 A=27、K=18，自己=7 比邻居都近 → 顶层结束，落脚 F
```

**第 0 层光束搜索（ef=3，约 10 次距离）**：
```
池 {F:7} → 弹 F 扩 E,G → {G:2,E:12} → 弹 G 扩 F,H → {H:3,E:12}
→ 弹 H 扩 G,I → {I:8,E:12} → 弹 I 扩 H,J → {J:13,E:12}
→ 弹 E 扩 D,F → {D:15,J:13} → 弹 J 扩 H,I → {D:15}
池里最近 D=15 > 已找到第 2 近 H=3 → 停止
```

**结果**：top-2 = G(25)、H(30)，距离 2 和 3，正确；全程 ≈13 次距离。

**诚实注脚（面试加分）**：11 节点小数据 HNSW（13 次）比暴力（11 次）还慢——**HNSW 优势只在数据量大**：10 万向量 HNSW 200~300 次 vs 暴力 10 万次。所以"小数据直接暴力 KNN，百万级才上 ANN/HNSW"。

- 面试一句话："两层查询：顶层从入口点贪心下降锁大致区域，第 0 层光束搜索扩候选池直到池里最近点不比第 k 近更近，返回 top-k；每次只访问 O(log N) 个小区域，玩具例子看不出优势，大数据才碾压暴力。"

### Q4：不同向量怎么排序？（向量没有天然大小，排序 = 按到 query 的距离排）

**核心认知**：数字是 1D 有天然全序（1<2<3）；向量是多维的，**没有"谁更大"的天然定义**（(100,0) 和 (0,100) 谁大？几何上到 q 距离可能一样）。所以"向量排序"完整说法 = **给定 query q，把候选向量按"到 q 的距离标量"排序取 top-k**。

**2D 例子**（q=(2,3)，候选 v3=(1,5) v1=(4,1) v2=(0,0)）：
```
欧氏距离 d(q,v) = √((qx-vx)² + (qy-vy)²)
d(q,v3) = √(1+4) ≈ 2.24
d(q,v1) = √(4+4) ≈ 2.83
d(q,v2) = √(4+9) ≈ 3.61
排序：v3 < v1 < v2 → top-1 = v3
```
几何直观：以 q 为圆心画同心圆，离圆心越近 = 距离数字越小 = 排越前。

**三个必须说透的点**：
1. **排序结果完全取决于 q 在哪**：换 q 排序立刻变。向量库没有"存好的全局有序表"，每次查询都是拿 q 现场算距离、现场排 → 所以必须 ANN 索引，作用是"少算"而非"预排序"
2. **换度量 = 换排序**：欧氏（直线距离）/ 余弦（只看方向）/ 内积（偏爱长向量）top-k 结果可能完全不同。例：v=(3,4)、w=(6,8) 方向相同，q=(1,0)：余弦下 v、w 一样近，欧氏下 v 更近。工程上度量是业务决策：文本语义常用余弦，坐标/数值常用欧氏
3. **回到 HNSW**："邻居谁更接近 query" = 同一套距离数字比较；光束搜索优先队列 = 按距离标量排序的堆。高维（768 维）原理一样，只是平方和从 2 维变 768 维

### Q5：ANN 索引是啥？（近似最近邻索引）

**ANN = Approximate Nearest Neighbor，用一点精度换巨大速度。**

**解决什么问题**：暴力精确搜索要和 N 个向量全算距离，N=1 亿时每次查询几百 ms~秒级。高维（768D）有维度灾难，点之间距离都差不多，剪枝结构（KD-tree）失效 → 精确搜索在百万级没戏。

**"近似"**：精确=保证返回全库最相似 k 个（100% 召回）；ANN=返回"大概率最近的"，可能漏掉真最近邻（召回 95~99%），但快几个数量级。
- 类比：百万人口城市找"最像我的10个人"——精确=挨家挨户比对；ANN=按区域分好/建高速路网，锁几个区域快速筛
- 为什么能接受：top-k 给 LLM 当上下文，漏第8第9名无感——精度掉 1~5%，延迟降 100~1000 倍

**"索引"**：离线建一次、在线快查询的预组织数据结构：
```
离线（一次性）：聚 K 簇（IVF）/ 建分层图（HNSW）/ 压缩短码（PQ）
在线（每次）：query 只访问相关小区域，算 O(log N) 次距离，返回 top-k
```
关键：索引**少算而不是预排序**——排序永远依赖 query（Q4），索引只让"要算距离的点"从 N 变几十个。

**四个 trade-off 指标（面试聊 ANN 必提）**：
| 指标 | 含义 | 代价 |
|---|---|---|
| 召回率 | 真 top-k 被找到比例 | 越高越慢 |
| 查询延迟 | 每次搜索耗时 | 越低越费索引 |
| 内存 | 索引空间 | HNSW 高、PQ 可压缩 |
| 构建时间 | 建索引耗时 | 大样本小时级 |

**标准句式**："ANN 用 1~5% 召回率换 100~1000 倍加速；HNSW 分层图 O(log N) 查询、IVF 只搜 nprobe 簇，Milvus/FAISS 落地。"GraphRAG 入口实体定位 = 实体向量建 ANN 索引（离线），问题走索引查 top-k（在线），毫秒级。

### Q5-追问：KNN / ANN / HNSW / Cross-Encoder 关系澄清（面试一字之差陷阱）

**① KNN vs ANN（精确 vs 近似）**

| 维度 | KNN（精确） | ANN（近似） |
|---|---|---|
| 结果 | 保证真·最近 K 个（100% 召回） | 大概率最近（召回 95~99%，可能漏真邻居） |
| 做法 | 全库暴力扫描，逐个算距离 O(N) | 离线建索引（HNSW/IVF/PQ），查询 O(log N) |
| 建索引 | 不需要 | 需要 |
| 适合数据量 | 几千~几万条 | 百万级及以上 |
| 工程接口 | FAISS/Milvus exact/brute-force 检索 | FAISS/Milvus index 检索 |

- 注意：KNN 在机器学习语境里还是分类算法（邻居投票）；检索语境 = 精确最近邻。
- 金句："KNN 全库暴力保证 100% 召回；ANN 靠索引用 1~5% 召回率换 100~1000 倍加速。小数据 KNN 直接算，百万级必须 ANN。"

**② ANN vs HNSW（类 vs 具体算法）**
- ANN = 一类方法的统称（近似最近邻搜索）；HNSW = ANN 家族里最流行的具体算法（FAISS/Milvus 默认主力）。
- 家族成员：IVF（k-means 聚簇，只搜 nprobe 个簇）、PQ（向量切段量化成短码，省内存）、LSH（哈希分桶）。
- 正确说法："用哪种 ANN 算法"，不是"用 ANN 还是 HNSW"——包含关系，类似"排序算法 vs 快排"。

**③ Cross-Encoder 精排（RAG 两段式检索的第二段）**
- 背景：**粗排（检索）** 用 bi-encoder（双塔）embedding + ANN 召回 top-100，快但粗；**精排（rerank）** 用 cross-encoder 对 top-100 逐条打分 → top-5 喂 LLM。
- 原理：bi-encoder 把 query 和 doc **各自独立**编码成向量（零交互，为了能离线预计算 doc 向量存库）；cross-encoder 把 query 和 doc **拼接成一句话** `[CLS] query [SEP] doc` 一起过同一个 Transformer，token 级交叉注意力（全交互），输出 0~1 相关性分。
- 为什么更准（例子）：
  - q="有哪些便宜的酒店" vs doc"xx 豪华五星酒店"：bi-encoder 在"酒店"语义上可能误召回，cross-encoder 看到"便宜"vs"豪华"反义 → 低分
  - q="不是苹果的平板" vs doc"Apple iPad Pro"：bi-encoder 向量接近（都是平板），cross-encoder 看到"不是"否定词 → 低分
- 代价：cross-encoder 无法预计算（必须现场拼接 q+doc），每候选一次前向 → 只能对 top-100 跑，不能全库。专用 reranker 模型（bge-reranker / Cohere rerank）。
- 金句："两段式检索：bi-encoder 粗排求全（ANN 召回 top-100），cross-encoder 精排求准（逐条打分取 top-5）。召回靠向量、排序靠交互，成本可控。"
- 项目映射（C 端客服）：问"秒杀A和竞拍B哪个划算" → 向量粗排召回 100 条玩法/商品 → cross-encoder 精排 top-5 → 注入 LLM 生成答案。

**④ Cross-Encoder 原理拆解：Transformer 内部到底怎么算（追问）**

- **输入是一条拼接序列，不是两个向量**：`[CLS] q1 q2 q3 [SEP] d1 d2 d3 [SEP]`，query 和 doc 的 token 拼一起，每个 token → embedding + 位置编码，送进同一个 Transformer
- **"cross"的本质**：拼接后走普通 self-attention（权重 = softmax(Q·Kᵀ/√d)），但 q 和 d 的 token 在**同一条序列**里互相 attend → token 级交互，每层信息跨 q/d 边界流动，L 层后全序列都是"带对方信息的混合表示"。对比 bi-encoder：两个静态向量，相似度=余弦，永远学不会"否定/反义/指代"
- **面试加分细节**：标准 cross-encoder 是"拼接+self-attention"，不是真正的 cross-attention 层（那是 encoder-decoder 里 decoder 对 encoder 的机制）；"cross"指跨 q/d 边界的交互
- **[CLS] = 关系压缩包**：每层 attend 全部 token，最后一层 h_CLS 是"q+d 关系"的联合表示（不是 q 向量也不是 d 向量）
- **打分头**：h_CLS → 线性层 → 1 个标量 logit → sigmoid → 0~1 分；对粗排 top-100 每条跑一次前向 → 排序 → 取 top-5（top-k = 打完分排序后的前几名）
- **分数怎么学出来**：训练样本 (q, 相关doc, 不相关doc) 或 (q,d,label)，对比/排序损失拉大相关对与不相关对的分数差 → 学"整句话组合后的相关性"
- **代价根源**：注意力 O((len_q+len_d)²×L) + q+d 无法离线预计算 + 输入限长（一般 ≤512 token）→ 只能精排 top-k，全库跑不起

**⑤ bi-encoder 算"几何相似度"，cross-encoder 算"学出来的相关性概率"（追问）**

- **bi-encoder 最后一步 = 固定几何公式**：sim(q,d)=cos(q_vec,d_vec)（或内积/欧氏距离），模型只产出向量，度量是人事先定死的；对称 sim(q,d)=sim(d,q)，只看夹角
- **cross-encoder 没有"相似度公式"这一步**：score(q,d)=σ(W·h_CLS+b) → 0~1，含义 = "模型判断 q 和 d 相关的概率"（BCE/对比损失训练学出来的映射），从输入到分数整条路径都是学的
- 类比：bi=用尺子量两个人身高差（固定公式）；cross=评委看完两人完整资料后打分（学出来的判断）
- 为什么重要：余弦在"固定语义空间"比夹角，天生看不见"不是/但是"这种改变整句含义的词；cross 先让 q/d token 交互、再让打分头判断，比的是"交互后的关系"而非"编码后的距离"，且可以学不对称关系（q 是问题、d 是答案）
- 面试一句话："bi-encoder 算的是固定几何度量（余弦/内积），cross-encoder 算的是学出来的相关性概率（[CLS] 过打分头 sigmoid）；一个量距离，一个学判断。"

**⑥ 注意力权重 ≠ 相似度分数：完整链路走查（追问）**

- **先纠正**：cross-encoder 是**双向注意力**（encoder 结构），每个 token 可以 attend 序列里**所有** token（前后都行），不只是前面的
- **完整链路（11 token 例子：[CLS] 不是苹果的平板 [SEP] Apple iPad Pro [SEP]）**：
  1. 每个 token → embedding → 投影出 Q/K/V（每头一组）
  2. 注意力（中间产物，不是最终分数）：token i 输出 = Σ_j softmax(Q_i·K_j/√d)×V_j → 每个 token 的表示变成全序列信息的加权混合，叠 L 层后 q/d 双方信息已融合
  3. [CLS] 聚合：最后一层 [CLS] 向量 h（如768维）= 整条 q+d 序列的"关系表示"
  4. 打分头（**这里才是相似度**）：score = σ(W·h+b) → 0~1 相关概率
  5. top-k：对粗排 top-100 每个候选完整跑一遍 1~4 → 100 个分数 → 降序 → 取前 5
- **两个层次的"相似度"别混**：
  | 层次 | 在哪算 | 是不是最终分数 |
  |---|---|---|
  | token 级 | 序列内部：注意力权重 softmax(Q·Kᵀ/√d)，"谁影响谁" | ❌ 造表示的工具 |
  | 序列级 | 打分头：score=σ(W·h+b)，"这条 q+d 多相关" | ✅ 排 top-k 的分数 |
- 直觉：注意力负责"看见关系"（把否定/反义/指代融合进表示），打分头负责"判断关系"（融合后的表示压成 0~1）；没有注意力做融合，打分头就只能拿两个独立向量判断（=bi-encoder 的局限）
- 面试一句话："注意力是造表示的工具不是相似度：token 输出=softmax(QKᵀ/√d)加权V，叠 L 层融合 q/d 信息；[CLS] 聚合成关系向量后打分头 σ(W·h+b) 才输出 0~1 分。top-100 每个候选跑一遍前向→排序→取前 5。"

**⑦ 打分机制 vs 逐 token 生成机制的区别（判别式 vs 生成式，追问）**

- **本质**：打分=判别式任务：整条序列一次编码 → 压成 1 个标量（相关概率），没有产出文字的过程；逐 token 生成=自回归任务：每一步用已生成的 token 预测下一个 token 的概率分布（softmax 过词表）→ 选一个拼进去 → 继续，输出一段文字
- **机制四区别**：
  | 维度 | 打分（encoder/BERT类） | 生成（decoder/GPT类） |
  |---|---|---|
  | 注意力掩码 | 双向：每个 token 看全序列 | 因果掩码：只能看过去（防偷看未来） |
  | 输出头 | 分类头：1 个 logit → sigmoid 0~1 | LM 头：词表 V 个 logit → softmax 概率分布 |
  | 训练目标 | 学"相关/不相关"（对比/分类损失） | 学"下一个词"（自回归交叉熵） |
  | 推理成本 | 一次前向 O(L²) 固定 | 每生成 1 token 一次前向，总成本 O(L²×T) 随输出长度线性涨 |
- **区别在任务范式不在模型**（面试加分）：BERT 预训练（MLM 遮词）是生成式目标、下游用分类头打分；GPT 也能打分（LLM-as-reranker：prompt 问"哪个文档更相关 A/B"，用输出 Yes/No 概率或困惑度当分数）。分界线=输出是"一个判断"还是"一段文字"
- **工程选型**：打分 reranker 一次前向出分、便宜、需标注数据；生成式打分要写一段话才判断、慢贵、但 zero-shot 能用且有理由可解释 → 线上精排用打分，无数据离线场景用 LLM-as-reranker
- 面试一句话："打分是判别式：一次编码压成 1 个标量；生成是自回归式：因果掩码下逐步预测词表概率。一个双向注意力+分类头，一个因果掩码+LM头；训练一个学'相关不相关'，一个学'下一个词'。"

**⑧ bi 和 cross 是"两种模型"还是"不同相似度计算"？为什么 bi 能离线？（追问澄清）**

- **关键纠正：两者都是 Transformer**（BGE/E5/text-embedding-3 全是 BERT 类 encoder）。区别不是"是不是 Transformer"，而是用法：
  | | bi（双塔） | cross（单塔） |
  |---|---|---|
  | Transformer 怎么用 | 分开用：q 塔、d 塔各自编码（可共享权重） | 拼起来用：q+d 一条序列 |
  | q/d 交互 | 永不交互 | token 互相 attend |
  | 产出 | 两个向量 → 余弦/内积 | 一个分数（学出来的概率） |
  | 有"不是 Transformer"错觉的原因 | 早期双塔的塔可以是 CNN/BOW 等任意编码器 | — |
- **是"架构不同"也是"计算方式不同"（因果链）**：双塔架构 → 产出两个独立向量 → 相似度=余弦/内积（几何公式）；单塔架构 → [CLS] 关系向量 → 相似度=学出来的概率（打分头）
- **为什么 bi 能离线（核心）**："离线"的本质 = **doc 的表示是否依赖 query**：
  - bi：doc 向量只依赖 doc 本身 → 离线全量编码存向量库+建 ANN 索引；在线只需 query 一次前向 → 库里 ANN 搜
  - cross：分数依赖 q+d 拼接 → doc 单独编码"没 query 就没法打分"→ 每个 query 现场和候选拼接跑前向 → 只能精排 top-100
- trade-off 根源：bi 用"doc 表示固定、无交互"换离线预计算+低延迟；cross 用"现场计算、全交互"换准
- 面试一句话："bi 和 cross 都是 Transformer，区别是用法：bi 双塔分开编码算余弦，cross 单塔拼接算概率；离线与否的本质是 doc 的表示是否依赖 query。"

**⑨ Milvus Segment：无索引的增量段会被检索吗？（向量库工程追问）**

- **会，而且必须查——走暴力扫描（brute-force），不是不检索**
- **Segment 生命周期**：Growing 段（增量区：接收新写入，可写可查）→ Sealed 段（封存不再写）→ 后台异步建索引（HNSW/IVF，秒~分钟级延迟）→ Compaction 合并小段成大段
- **为什么无索引也查**：保证**写后立即可见**（read-after-write）——刚入库的商品/实体必须马上能搜到，索引异步构建不能等
- **混合检索机制**：查询时所有 segment 都会被扫——有索引段走 ANN（HNSW），无索引段（增量区/未建索引）走全量暴力扫描（逐个算距离），结果合并排序取全局 top-k
- **代价与兜底**：无索引段越大暴力扫越慢 → 工程四板斧：控制 Growing 段大小（≤512MB 就 seal）、及时封存+触发建索引、compaction 合并、查询并行扫多段
- **类比 LSM-Tree（面试加分）**：Growing 段≈memtable（无索引直接查），Sealed+Compaction≈刷盘+SSTable 合并——同样的"写快、读靠后台整理兜底"取舍
- 面试一句话："Milvus 是混合检索：有索引段走 ANN、无索引段走暴力全扫、合并取 top-k。无索引不是不检索，是为了写后立即可见；代价是扫描慢，靠控制段大小+及时建索引+compaction 兜底。"

**⑩ 标量量化 SQ：4 字节→1 字节，4 字节存的是什么？（向量压缩追问）**

- **4 字节 = float32（IEEE 754），存的是向量每个维度的浮点坐标值**：768 维 = 768×4 = 3072B ≈ 3KB/条
- **标量量化 SQ8** = 逐维度把浮点均匀映射成 1 字节整数（0~255）：统计每维 min/max → q = round((value−min)/(max−min)×255) → 反算（有损）value ≈ min + q/255×(max−min)
- 例子：某维 min=−1.0,max=1.0，v=0.35 → q=round(1.35/2×255)≈172；反算 0.349（误差 0.001）
- **min/max 表**：每维一对 min/max（2×d 个标量，很小）；查询时把 query 也量化到同一整数空间，直接在整数域算距离
- **收益 vs 代价**：内存省 4 倍（3KB→768B）+ 整数运算 SIMD 友好更快；召回降 1~5%（量化误差）——这就是 ANN 四指标"内存↔召回"的实操
- **SQ vs PQ**：SQ=逐维均匀量化（简单）；PQ=分段码本量化（可压到几比特/维度，更狠）；常配合 IVF/HNSW
- 面试一句话："4字节存的是 float32 浮点坐标；SQ 按每维 min/max 均匀量化成 1 字节整数（q=round((v−min)/(max−min)×255)），query 同样量化后在整数域算距离——4 倍省内存、整数更快，召回降 1~5%。"

### Q6：分层图到底怎么建的？（不是按顺序分层，是随机升层 + 最近邻连边）

**误区纠正**：1D 数字例子（0,5,10,15,20 排好序）只演示"搜索怎么走"，容易误以为层=有序。HNSW 学的**不是跳表的"有序"，而是跳表的"随机升层"**——向量没有顺序，只有距离。

| | 跳表 | HNSW |
|---|---|---|
| 底层结构 | 有序链表（数字排好） | 无序最近邻图（无顺序，只有距离） |
| 高层是啥 | 隔几个挑一个（有序子集） | **随机**挑一批点（与大小无关） |
| 搜索方向 | 向右（顺序）+ 向下 | 向"离 query 最近的邻居"走 + 向下 |
| 升层机制 | 抛硬币随机升层 | 抛硬币随机升层（一样） |

**① 每个点属于哪些层 = 抛硬币随机升层**：先在第0层，以概率 p（如1/2）升第1层，再 p 升第2层……直到不升。结果：~1/2 的点只在第0层，1/4 在第0+1层，1/8 到第2层 → 高层是随机稀疏子集。

**② 每层是什么图 = 最近邻图（proximity graph）**：边不按顺序连，**按距离连**——该层出现的点里，每个点连到离它最近的 M 个邻居。
2D 例：A(0,0) B(1,0) C(0,1) D(3,3) E(4,3) G(10,10)，随机升层 A,G→第2层，B,D→第1层，C,E→仅第0层
- Layer 2={A,G}：互连，距离~14 → **长跳边**（子集稀疏→"最近邻"也隔很远）
- Layer 1={A,B,D,G}：A─B（近）、A─D、D─G（远跳）
- Layer 0=全部：连真·最近邻 A─B、A─C、D─E 短边，精确

**关键认知**：高层长跳边**不是"有序前几名"，是"随机子集里最近邻也隔得远"**；第0层人全，边全是短距精确。

**③ 插入新点流程**：
```
① 抛硬币定层数（如抽到第1层 → 出现在 Layer0+1）
② 从最高层入口贪心搜索定位（Q3 那套）——不在的层只路过校准方向
③ 降入所在层：贪心找最近 M 个点 → 双向连边
④ 每层都连边；某点边数超上限 M 时，用"方向多样性启发式"删冗余边
   （保留指向不同区域的邻居，防止边全堆一个方向）
```

**④ 为什么随机分层能搜准**：高层是全局均匀随机抽样，任何区域都大概率有高层点落脚 → 从顶层入口总能快速跳到大致区域；逐层下降逐步校准；第0层全量精确收尾。

**一句话**：HNSW = 跳表的随机升层（分层思想）+ 最近邻图（无序世界的连边方式）；搜索每层"向更近邻居走"，局部最优再降层。

### Q7：LightRAG 到底如何检索的？（双层检索 + 四种模式）

**索引阶段（3 步，比 GraphRAG 少 2 步最贵的）**：
```
① 切块：1200 token/块，100 token 重叠
② 实体+关系抽取：LLM 从每块抽实体/关系
③ 键值对化+去重：每个实体/关系=(Key, Value)
   Key=便于匹配的短语（实体名/关系关键词），Value=详细描述（组装上下文用）
   同名合并：刘备抽 82 次 → 合并成 1 节点；不做语义去重（AI vs Artificial Intelligence 保留）
   理由：查询时相似实体会被多路召回一起捞出来
存储：知识图谱（实体=点/关系=边，NetworkX/Neo4j）+ 向量库（实体描述、关系描述、关系关键词三类向量）
```

**查询阶段（4 步，核心是"1 次 LLM 抽词 + 两路并行检索"）**：
```
① 关键词抽取（1 次 LLM 调用）
   问题"国际贸易如何影响全球经济稳定？" →
   high_level=["国际贸易","全球经济稳定","经济影响"]（抽象主题）
   low_level=["贸易协定","关税","货币汇率","进口","出口"]（具体对象）
② 双层检索（两路并行）
   Low-level：低层关键词 → 向量库搜【实体节点】（点）
              → 从入口实体沿图扩【一跳邻居】：关系+描述+原始文本块
   High-level：高层关键词 → 向量库搜【关系边】（线）
              → 聚合关系涉及的实体+更高层语义
③ 上下文组装：两路拼一起，控制总 token（默认~4000），按相关性裁剪
④ LLM 生成：上下文+原始问题喂 LLM
```

**四种查询模式**：
| 模式 | 用什么检索 | 适用 |
|---|---|---|
| Naive | 纯向量检索文本块（=传统RAG） | 简单事实问答 |
| Local | 只用 Low-level（找实体） | 具体实体类："这个 API 怎么用" |
| Global | 只用 High-level（找关系/主题） | 抽象归纳："最近转化率为什么降" |
| Hybrid（默认） | Low+High 并行 | 复杂综合问题 |

**vs GraphRAG（面试背这个表）**：
| | GraphRAG | LightRAG |
|---|---|---|
| 全局问题 | 离线预生成社区摘要，查询 Map-Reduce 遍历几百上千社区 | 查询时现场拼：抽高层关键词直接搜关系边 |
| 每查询 LLM 调用 | 几百上千次 | 1 次抽词 + 少量向量检索 |
| 索引成本 | 上万个 LLM 调用 | 省社区层 → **Token 降 99%** |
| 增量更新 | 重跑社区检测 | 抽完直接 upsert 追加 |
| 代价 | 贵、慢 | 全局深度洞察弱（社区摘要是 LLM 加工过的层次抽象，LightRAG 是现场拼凑） |

**一句话**：GraphRAG 靠预先建好的社区摘要答全局题（重但深）；LightRAG 靠"拆高低两层关键词，一路搜实体点、一路搜关系线"现场拼全局（轻但浅）。

**项目映射（直播电商智能助手）**：C 端问"秒杀活动A价格为什么比日常贵" → Low-level 搜「秒杀活动A/价格」实体+一跳邻居，High-level 搜「促销玩法→定价规则」关系，Hybrid 模式；OnCall 问"最近转化率为什么降" → 偏 Global（搜关系/主题）。


## 五、Agent 反思机制（Reflexion）

> 参考：小林《图解Agent · 15 讲讲 Agent 的反思机制》
> https://xiaolinnote.com/ai/agent/15_reflection.html

### Q1：Reflexion 的"错题本"怎么建设、怎么读取？是放在 RAG 吗？

**一句话**：Self-Refine = 写完作文当场改；Reflexion = 把犯的错记在本子上，下次写之前先翻笔记（Shinn et al. 2023，引入"经验记忆 episodic memory"）。

**① 错题本怎么建设（写入端）**：
- 触发：任务**失败后**（评估不通过），做一次任务级反思，产出教训条目
- 存什么：**不是错误输出本身，而是提炼后的反思文本**——"这类 bug 的成因和避免方法"
  ```
  ❌ 错误输出："库存扣减成功但商品卡没更新"
  ✅ 教训："秒杀类问题：库存写库成功≠展示更新。先查 Redis key
            seckill:stock:xxx 是否过期，再查扣减流水。验证顺序：DB→缓存→展示层"
  ```
- 结构化：带元数据 `{type(任务类型tag), reflection(教训正文), created_at}`
- **防膨胀三原则**：去重（同类教训合并）、上限（每类只留最近 N 条，episodic buffer 有长度限制）、老化（架构变了 mark stale，验证后再用）

**② 后续怎么读取（读取端）**：
- **Reflexion 原版 = 不检索，直接塞上下文**（小林原文："类似"通过把经验记忆塞到当前任务上下文，让 LLM 生成时参考，而不是靠严格的相似度匹配检索）
- 流程：新任务开始/失败重试前 → 取最近 N 条经验 → 拼进 system prompt/few-shot 当"注意事项" → LLM 主动规避
- 工程升级：错题膨胀后 → 按 type tag 过滤 + 向量检索 top-k 注入

**③ 是放在 RAG 吗？**
| 方案 | 做法 | 何时用 |
|---|---|---|
| 原版 Reflexion | 不检索，episodic buffer 最近 N 条全量塞 prompt | 错题少（<50 条） |
| RAG 化错题本 | 教训+embedding 存向量库，相似度检索 top-k 注入 | 错题多、类型杂 |
| 普通文件/DB | md / SQLite 存结构化教训 | 要人可读、git 维护 |

**核心认知**：原版 Reflexion **不是 RAG**（按时间顺序全量塞）；工程上膨胀后可 RAG 化（按相关性动态召回）。本质都是"经验记忆"= 记忆机制里的 feedback/失败经验型记忆，套同一架构：**索引常驻 + 正文按需**。

**面试标准答法**："Reflexion 错题本三层：失败 → 反思 LLM 提炼教训入库（带任务类型 tag）→ 新任务取同类最近 N 条拼进 prompt 规避；错题超百条改向量检索 top-k 注入（RAG 化）。原版不检索，检索化是我的工程扩展，用来治膨胀。"

**项目映射（直播电商智能助手）**：OnCall 排障失败案例 → 按场景 tag 入库；C 端客服 Guardrail 拦下的幻觉案例 → 存错题本下次规避 → "三层防幻觉 + Reflexion 闭环"面试亮点。

### Q2：ReAct / Plan-and-Execute / Reflection 是包含关系还是并列？（正交可组合）

**结论：不是包含、不是简单并列——是两个执行策略（可嵌套）+ 一个质量闭环（可叠加）的正交关系。**

| 范式 | 回答的问题 | 核心机制 | 维度 |
|---|---|---|---|
| ReAct | 每一步怎么执行 | Thought→Action→Observation 循环，边想边做 | 执行策略·单步 |
| Plan-and-Execute | 任务怎么拆、顺序、跑偏怎么调 | Planner 出清单 → Executor 逐步执行 → Re-planner 动态调整 | 执行策略·全局编排 |
| Reflection/Reflexion | 做得对不对、怎么改进 | 生成→评估→改进闭环；Reflexion 把失败经验存错题本下次参考 | 质量闭环 |

**① ReAct vs Plan-and-Execute = 同一维度，搭配使用不是二选一**（小林原话："ReAct 负责每一步怎么执行，Plan-and-Execute 负责这些步骤的整体编排和动态调整。两者不是替代关系，而是经常搭配使用"）：
```
Plan-and-Execute（外层编排）
  Planner → Executor（每步内部 = ReAct 循环）→ Re-planner（检查进度、动态调整）
```
Plan-and-Execute = 在 ReAct 上**加一层全局规划**（编排层套执行层），不强制内部用 ReAct。

**② Reflection = 另一维度，叠加在任何执行策略上**：ReAct 每步后可挂步骤级反思；Plan-and-Execute 任务完成后挂任务级反思；Reflexion = 失败经验入库，下次同类任务前先翻错题本。

**三者共存图**：
```
用户任务
  ├─ Plan-and-Execute（维度A：编排）Planner→Executor(=ReAct)→Re-planner→…
  └─ Reflection（维度B：质量闭环，叠加）每步/任务完成→评估→不过关→改进/重试
```
LangGraph 一个状态机里同时有规划节点、执行节点（ReAct 循环）、反思节点、记忆节点——就是"正交可组合"的实证。

**工程选型**：简单单工具任务=ReAct 够用；多工具多环节复杂任务=Plan-and-Execute（先全局规划防跑偏，规划用强模型/执行用便宜模型省成本）；质量要求高=只在关键节点开 Reflection（每轮多 1 评估+1 改进调用，别全程开）。

**项目映射（OnCall 助手）**：Plan-and-Execute 编排（查日志→查指标→定位根因→给建议）+ Executor 里 ReAct 调工具 + 排障失败写错题本（Reflexion）——三层正交叠加。

### Q3：Codex / Claude Code 里三种范式是混合用的吗？

**是的，但不是"三个模式切换"，而是运行时默认混合：ReAct 做主干、Plan 做骨架、Reflection 做护栏。**

**Codex 里的落点**：
| 范式 | 落点 |
|---|---|
| ReAct | 主循环本身：思考 → 调工具（exec_command/apply_patch）→ 观察输出 → 继续 |
| Plan-and-Execute | `update_plan` 工具：多步任务先列计划（步骤+状态），边执行边更新 in_progress/completed（Planner+Re-planner） |
| Reflection | ①工具失败自动修正重试（观察→发现报错→换参数重试）②用户自定义 skill 强制检查点：task-status-report（每次回复检查上任务是否完成）、git-verify-push（推送后验证远端）、algorithm-unfinished-check（每日进度检查） |

**最有说服力的证据**：用户自己的 skills（git-check-before-commit-push、truncate-long-output）就是"执行后评估、不达标就纠正"的 Reflection 工程化，做成 skill 形式 = 反思节点。

**Claude Code 里的落点**：
| 范式 | 落点 |
|---|---|
| ReAct | 主循环同样：推理 → 工具（Bash/Edit/Read）→ 观察 → 循环 |
| Plan-and-Execute | Plan mode（先出计划给用户确认再执行）+ task list（Re-planner） |
| Reflection | ①测试失败 → harness 自动读报错→修复→重跑（self-correction）②`/compact` 反思式摘要 ③新版 Memory 工具自动沉淀 feedback 记忆（=Reflexion 错题本的产品化雏形） |

**核心认知（面试背）**：三种范式在生产 Agent 里是三个层次不是并列选项——
```
ReAct = 主干：每轮"想→做→看"（管单步）
Plan  = 骨架：多步任务先列计划、边做边更新（管全局）
Reflection = 护栏：失败重试、强制检查点、经验沉淀（管质量）
```

**面试标准答法**："我不把三种范式当模式切换。生产级 Agent 框架是 ReAct 主循环做主干，内嵌 Plan 工具做全局规划、失败重试和评估检查点做 Reflection，三者在同一个状态机里正交共存。我的项目同样：LangGraph 里规划节点+执行节点+反思节点一张图。"


## 六、Agent 任务拆分（面试必问）

> 参考：小林《Agent面试题 · 7 复杂任务怎么做的任务拆分？》
> https://xiaolinnote.com/ai/agent/7_tasksplit.html

### Q1：复杂任务怎么做的任务拆分？为什么要拆分？效果如何提升？

**三个层次才完整：为什么拆 → 怎么拆 → 拆完还要做的三件事。**

**第一层：为什么拆（核心 = context window 有限）**
- LLM 工作台（context window）有上限，任务越大中间状态越多 → "桌面太乱"，模型难以持续追踪当前子目标
- 原例：写竞品分析报告 = 搜竞品信息+功能对比+优缺点+写结论四件事混一起 → 搜索时掺分析、写表格时引入新信息、写到一半忘数据、输出"什么都有什么都不深"
- 额外好处：每步独立输出可单独检查验证，出错只重试那一步

**第二层：怎么拆**
| 拆分方式 | 做法 | 适用 |
|---|---|---|
| 静态拆分 | 提前写死步骤（固定 SOP） | 流程固定，稳定可控 |
| 动态拆分 | LLM 自己规划（Plan-and-Execute） | 流程不固定，灵活但质量不稳定 |

- **递归拆分**：拆成任务树，只有真正做不好的节点才继续拆，拆到**原子粒度**（一步一件事）就停；任务越复杂层数越深，计算开销和难度成正比（不一刀切）

**第三层：拆完还要做的三件事**
1. **依赖分析 + 并行优化**：识别步骤依赖，能并行的并发跑 → **关键路径时间降 40%~60%**（数字必报）
2. **Replan 机制**：每步执行完把"本步结果+剩余计划"交给规划模块判断还合理吗，不合理就重生成剩余计划；**折中**：设触发条件（输出与预期差异大/执行失败）才 Replan，不每步触发（否则每步多一次 LLM 调用）
3. **拆分验证标准**：
   - 完备性：步骤拼起来覆盖原任务全部要求（逐项对照无遗漏）
   - 独立性：职责边界清晰不重叠（反例：步骤2"搜索功能"vs步骤3"分析核心能力"会搜到同一批内容 → 重复劳动+汇总矛盾；好拆法：一个搜集一个加工）
   - 可验证性：每步带**验收标准**（像单元测试断言，如"输出必须含价格数字+计费模式"），执行完自动检查，缺了就自动重试

**粒度**：以原子操作为准——太细步骤数爆炸（每步一次 LLM 调用），太粗一步还是复杂（桌面还乱）。

**项目映射（OnCall 助手）**：动态拆分（补参追问→并行查 Prometheus║Loki║发布║CMDB）+ 依赖并行（40-60%收益）+ 每步验收标准（数据缺字段自动补查）+ Replan（查到一半发现是发布问题→计划切换查发布单/回滚状态）。

**面试标准答法**："任务拆分三层：为什么拆——context window 有限、任务越大桌面越乱、拆开后每步可独立验证重试；怎么拆——静态（流程固定写死）vs 动态（LLM 规划），复杂任务递归拆到原子粒度，开销和难度成正比；拆完——依赖分析并行跑（关键路径降 40-60%）、Replan 按条件触发、每步带验收标准。粒度以原子操作为准。"

### Q13：实体记忆存在哪？（索引 vs 实体的最终澄清）

**实体记忆（真正内容）存在"仓库层"，不在 MEMORY.md 里。**

**Agent 记忆语境**：
| 层 | 存什么 | 存在哪 |
|---|---|---|
| 索引层 | name + description 一句话目录 | MEMORY.md（常驻 system prompt） |
| 实体层 | 记忆正文 text + 语义向量 | SQLite memories.db（新版）或独立 md 文件（旧版） |

SQLite 里：
```
memories 表：id | content(text 实体正文) | type | created_at ...
memory_embeddings 表：memory_id | embedding(BLOB 768维，只用来检索)
```
**关键**：实体记忆 = memories.content；向量是检索用的副本不是实体本身；MEMORY.md 那行索引不是实体，只是目录。

**GraphRAG 语境**：
| 东西 | 存在哪 |
|---|---|
| 实体节点+关系边（图结构） | 知识图谱 NetworkX/Neo4j |
| 实体/关系描述向量 | 向量数据库（Milvus/FAISS，给"定位入口实体"ANN 用） |
| 社区摘要（GraphRAG） | 额外一套（LightRAG 省掉） |

分工：向量库管"找入口"（图外），图库管"扩邻居"（图上），两步分开。

**Reflexion 语境**：失败教训实体存 episodic buffer——原版内存文本列表（最近 N 条全量塞 prompt）；工程版 SQLite/md（带 type tag）；膨胀后向量库（RAG 化 top-k）。

**一句话**：所有实体记忆都存"仓库"（SQLite/图库/向量库/文件），MEMORY.md 永远只放索引——实体进常驻会爆 token，索引进常驻让模型"知道有什么"，要用才去仓库取。

### Q14：短期记忆是不是存在各种 .md 文件里？（不是，正好反了）

**短期记忆 = 当前会话的上下文窗口，不存文件；各种 .md 是长期记忆（静态声明式层）。**

**短期记忆在哪**：
```
= system prompt + 最近 N 轮对话 + 工具调用历史与结果
存在"模型脑子里"（上下文窗口，内存态）
生命周期：会话结束就没了（只留 conversation.jsonl 存档日志——那是日志不是记忆机制）
管理：滑动窗口（太老滚出）+ Compact 压缩（太长→压成摘要插回上下文）
```
活例子：Codex 线程 21 万字符超限 = 短期记忆爆了。

**.md 全部是长期记忆**：
| 文件 | 记忆类型 | 生命周期 |
|---|---|---|
| AGENTS.md / CLAUDE.md | 静态声明式长期记忆（人写规则） | 永久，每次会话加载 |
| MEMORY.md | 长期记忆索引目录 | 永久，常驻 system prompt |
| SKILL.md | 可复用经验 | 永久，用到才加载全文 |
| SQLite memories.db | 动态长期记忆仓库（正文+向量） | 永久，按需检索 |

**为什么有错觉**：运行时 .md 被加载后和短期对话一起出现在同一个 context window——但存储与生命周期完全不同。**判断标准就一个：关掉会话后这东西还在不在？在=长期（磁盘），不在=短期（内存）。**

**面试金句**："短期记忆=当前上下文窗口，内存态、会话级、靠滑动窗口+Compact 管理，不落盘；.md 是长期记忆声明式层，落盘、跨会话。运行时两者一起进 context，但生命周期完全不同。"


## 七、推理增强：CoT → ToT → GoT

> 参考：小林《图解Agent · 14 如何赋予 LLM 规划能力》
> https://xiaolinnote.com/ai/agent/14_planning.html

### Q1：ToT（Tree of Thoughts）怎么实现的？

**一句话**：把 CoT 的"一条推理链"升级成"一棵推理树"——同时探索多条路径，LLM 负责生成候选和评估，代码负责树搜索（生成→评估→剪枝→深入），本质 = 带 LLM 评估的 beam search。

**四个核心组件**：
| 组件 | 是什么 | 实现 |
|---|---|---|
| 状态 State | 树节点 = 中间推理结果 | 文本表示（如 24 点里"当前凑出的表达式"） |
| 候选生成 | 从当前状态生成 k 个候选下一步 | 采样（同一 prompt 采样 k 次）或提议（LLM 一步步提出） |
| 状态评估 | 候选值不值得深入 | LLM 打分/投票（sure/likely/impossible）或值函数给 0-1 分 |
| 搜索算法 | 怎么在树上走 | BFS（每层保留 top-b 束宽）或 DFS（带回溯） |

**关键**：候选生成 + 评估都是 LLM 的活（生成 prompt + 评估 prompt）；剪枝/回溯/束宽是代码的活。**评估剪枝是灵魂**——不剪 = 暴力枚举（k=5、深 4 → 最多 5⁴=625 节点），剪了才是思维树。

**24 点例子（论文原例，4 9 10 13 → 24）**：
```
① 候选生成："列出下一步可用表达式" → 4*9=36 / 10-4=6 / 13-10=3 ...
② 评估："每个中间表达式距 24 多近？" → sure/likely/impossible → 剪掉 impossible
③ BFS：每层保留 top-b，直到某状态=24（如 (10-4)*(13-9)=24）或回溯换分支
```

**CoT vs ToT 对比**：
| | CoT | ToT |
|---|---|---|
| 结构 | 一条线性链 | 一棵树，多路径 |
| 纠错 | 走错全错，无回溯 | 边走边评估，剪烂分支，可回溯 |
| 探索 | 一条路走到黑 | 每层 k 候选 + 保留 b（beam） |
| 代价 | 1 次生成 | **3~5 倍调用**（每节点=生成+评估各一次） |
| 工程 | 改 prompt 一行字 | 要写搜索框架 |

**工程判断**：准确率要求极高 + 任务可拆成"可评估中间步骤"（数学/代码调试/规划）才值得；简单问答 3~5 倍调用纯浪费。成本数字必报：**典型调用是 CoT 的 3~5 倍**。

**项目映射（OnCall 排障）**：根因假设=候选生成（缓存过期/发布变更/DB慢查询），逐条查证据=评估，查不通剪掉、查通深入=BFS 剪枝——"多根因假设树 + 逐层验证剪枝，避免单一路径查到死胡同"。

### Q2：DeepSeek 的思维链 vs ToT？思维树在哪用、怎么实现？

**先分清三个层面**：
| | 谁控制 | 怎么来的 | 结构 |
|---|---|---|---|
| 经典 CoT（prompt） | 你（应用层加"请一步步思考"） | 任意模型+一行 prompt | 线性单链 |
| DeepSeek-R1/o1 思维链 | 模型（内部能力） | RL 训练，隐藏推理 tokens | 给你看线性化的，内部其实多路径探索+自我纠错（"等等这里不对"就是回溯痕迹） |
| ToT（思维树） | 你（应用层编排代码） | 你写搜索循环，LLM 只负责生成+评估 | 显式一棵树 |

**思维树在哪用**：不在聊天产品给用户看（成本 3~5 倍+没法展示）——用在应用层编排场景：数学/逻辑解题、Agent 排障（多根因假设）、代码调试、规划。LATS = ToT+MCTS+反思。Codex/Claude Code 的工具报错重试就是浅层版 ToT（试错即回溯换分支）。聊天产品把树折叠成"线性思维链"给用户看。

**ToT 怎么实现**（vs CoT 一行字）：
```
def solve(problem):
    states=[problem]
    for step in range(max_depth):
        candidates=[]
        for s in states:
            cs = llm_generate(prompt_generate, s)      # ①生成 k 候选
            for c in cs:
                score = llm_evaluate(prompt_evaluate,c) # ②评估打分
                candidates.append((c,score))
        states = top_b(candidates)                      # ③剪枝留 top-b
        if solved(states): return answer
    return best_candidate
```
落地：手搓（两个 prompt+API 调用几十行）/ LangGraph（生成/评估/条件边剪枝成状态图）/ tree-of-thoughts 库。
**成本公式**：每层 = 状态数×(1 生成+1 评估)，k=5/深4/束宽3 时几十次调用，是 CoT 的 3~5 倍。

**面试一句话**："CoT 是加一句 prompt 的线性单链；ToT 是用代码维护一棵树，LLM 只干生成候选和评估打分，剪枝回溯是我的循环做的。DeepSeek 展示的思维链是模型内部推理能力，和应用层 ToT 不是一个层面。"

### Q3：ToT 比 CoT 多哪些"思考"？（24 点完整对比）

**24 点：4 9 10 13 → 24（有解 (13−9)×(10−4)=24）**

**CoT（线性）**：先走 4×9=36 → 36±10/13 都凑不出 → 换 4+9=13 → 130−13=117 不行 → 死胡同里原地打转 → 错误结论"凑不出 24"。先走哪条全看第一感觉，钻进死胡同就出不来。

**ToT（树）**：
```
第1层·生成 8 候选：4+9=13 / 4×9=36 / 10−4=6 / 13−10=3 / 13+9=22 / 13−4=9 / ...
第1层·评估打分：10−4=6→likely（6×4=24，还差凑4：13−9=4✓）
                4×9=36→impossible（剩10,13凑不出24）
                13+9=22→impossible（剩4,10凑不出24）...
第1层·剪枝：保留 top-2 → [10−4=6, 13−10=3]
第2层（从6深入，剩4,9,13）：13−9=4→sure
第3层：6×4=24 ✓ 返回 (10−4)×(13−9)=24（失败则回退其他分支=回溯）
```

**ToT 比 CoT 多的四件事**：
| 多的东西 | CoT | ToT |
|---|---|---|
| ① 多路候选 | 每步一条路，靠感觉选 | 每层并行生成 k 个候选 |
| ② 中间评估 | 不评估走到哪算哪 | 每候选被 LLM 打一次分（sure/likely/impossible） |
| ③ 主动剪枝 | 无 | impossible 提前砍掉，省下后续深度 |
| ④ 可回溯 | 死胡同原地打转 | 分支失败回退到保留的其他分支 |

**代价**：多出来的思考 = 每节点多一次评估调用 → 总调用是 CoT 的 3~5 倍 → 只在"错一步代价极高"的任务用。

**项目映射（排障）**：CoT 排查"转化率下降"= 流量→页面→下单一条链查到底，最后发现是库存问题全白查；ToT = 并行生成 5 假设（流量/性能/库存/价格/风控）→ 每条查 1~2 证据打分 → 剪掉不符的 → 深入最强 1 条，失败回退次优假设。

### Q15：记忆三颗雷（面试必避坑）——向量检索 / 粒度 / 两层时机

> 参考：小林《Agent面试题 · 9 长短期记忆》https://xiaolinnote.com/ai/agent/9_memory_storage.html

**雷1：长期记忆="存数据库靠关键词搜索" ❌**
- 反例：用户昨天说"代码简洁、变量用英文"，今天问"帮我写爬虫脚本"，LIKE 关键词匹配 → "写爬虫" vs "Python风格偏好" 词面不重叠 → 搜不到
- 正解：Embedding+向量数据库语义检索。存储"代码简洁、变量用英文"→向量；query"写爬虫脚本"→同一模型向量 → ANN 命中语义最近的记忆
- 原理（RGB 类比）："苹果公司的产品策略" vs "Apple 的产品线规划" 文字不同但语义相近→向量近；"苹果公司" vs "猫吃鱼"→向量远
- 对比：关键词=字面匹配，同义词/换说法全漏；向量=语义相似，同义表达命中

**雷2：粒度越细越好 ❌**
- 反例：偏好"回复要简洁"拆成4条（简洁/讨厌啰嗦/先给结论/用列表）→ 检索只命中2条 → 拿到碎片化信息，忘了"用列表" → 输出仍不符合偏好
- 合理粒度 = **一次完整交互 / 一个独立知识点**：偏好类="先给结论再给证据、用列表、不要长总结、必要时附diff"一条；事件类=一次排障（现象+根因+解决+验证）一条
- 太粗也不行：整段对话存一条 → 命中大杂烩，细节被稀释还占token
- 判断标准：这条记忆被单独检索出来用时，信息完整吗？能独立支撑一个用途吗？

**雷3：搞不清两层记忆作用时机 ❌**
- 完整例子：任务1"优化代码，简洁英文变量名"→短期工作台记录中间状态→结束 clear→沉淀长期记忆"偏好：简洁、英文变量名"
  任务2（明天）"写爬虫脚本"→**任务前**长期记忆语义检索注入偏好→**任务中**短期工作台记中间状态→输出符合偏好的代码
- 时机分工表：
| 时机 | 用哪层 | 干什么 |
|---|---|---|
| 任务前 | 长期记忆 | 检索相关记忆注入 prompt（带过去经验开场） |
| 任务中 | 短期记忆 | 工作台记中间状态，保证不中途失忆 |
| 任务后 | 短期清空+长期写入 | 擦工作台；值得跨任务的沉淀向量库 |
- 反例：长期记忆当工作台（频繁检索→延迟高+拿到过时快照）；短期记忆不清理当长期（桌面越来越乱+爆 context）
- 金句："短期=任务执行中的工作台，任务结束清空；长期=任务前检索注入、任务后写入沉淀。一个管不中途失忆，一个管跨任务积累。"

### Q15-追问：三颗雷·详细走查例子（已入文档，复习用）

**雷1 展开：一次检索的全过程对比**
场景（OnCall 助手）：周一沉淀记忆"排障经验：转化率骤降→先查库存快照延迟→根因 binlog 消费积压"。周四新任务："ID 区转化率也降了，帮我看看"。
- 关键词检索：query 分词"转化率/降"→ LIKE 匹配原句 → 恰好命中算运气；一旦换说法"ID 区 GMV 掉得厉害，是不是库存数据不对？"→ "GMV/掉/库存不对" vs 记忆"转化率/降/快照延迟"字面几乎不重叠 → 全漏 → 零经验注入，从零开始查
- 向量检索：两条都 embed，"GMV 掉得厉害"和"转化率骤降"在语义空间距离很近（都是"业务指标异常下跌"）→ ANN 命中 → 开局直接有排查方向
- 加分点（面试说出口值钱）：关键词不是没用，适合做**硬规则过滤**（"记忆绑定 region=SG，query 提到 SG 才取"）；主检索走向量，再叠 BM25 做 hybrid，用 **RRF（倒数排名融合）** 合并两路——正好用上前面的 RRF。既防"同义换说法漏检"，又防"纯向量偶尔抓错语义"
- 金句：长期记忆核心 = Embedding+向量数据库，按**语义相似度**检索而非字符串匹配；关键词只做规则过滤或 hybrid 的一路

**雷2 展开：碎片化 vs 合理粒度**
- 碎片化走查（偏好类）：偏好拆 5 条入库 M1"回复要简洁"、M2"先给结论再给证据"、M3"能用列表就不用段落"、M4"总结≤3行"、M5"讨厌重复已说内容"。某任务 top-k=3 → 命中 M1/M2/M5，漏 M3/M4 → 输出没列表、总结写 8 行 → 用户仍不满意，且复盘时不知道漏了哪条——碎片化让检索质量不可控
- 正确做法：合并成一条完整偏好"回复风格：先给结论再给证据→能用列表就用列表→总结≤3行→不重复已说内容→必要时附diff"。一次命中即完整，检索结果=最终行为，行为可预期
- 事件类走查：一次排障存"现象+根因+解决+验证"一条（"09-14 SG 转化率骤降：现象 GMV-40%/时长+15%；根因 binlog 消费积压→库存快照延迟；解决扩容消费组；验证 2h 恢复"）。下次"转化率降"检索到 = 完整复用路径；若拆成现象/根因/解决三条 → 命中"根因"那条没头没尾，没法指导操作
- 判断标准一句话：**这条记忆被单独检索出来时，信息完整吗？能独立支撑一个用途吗？** 能→粒度合适；不能→太碎（合并）或太粗（拆开）

**雷3 展开：两层记忆配合的一次完整生命周期（OnCall 助手走查）**
周一任务1"查 SG 区直播转化率为什么降"：
1. 任务前：长期记忆检索 → 命中上周"活动日转化率假性下降"经验 → 注入 prompt，开局不盲目
2. 任务中：短期工作台实时记录：已查 region=SG / 活动日 / 快照延迟30min / 怀疑 binlog 积压 / 下一步看消费组 lag —— 中间状态全在工作台，**限流/中断也能续上**（呼应 task-status-report 技能）
3. 任务后：短期清空；长期写入"09-14 SG 转化率骤降根因=binlog 积压→快照延迟，解决=扩容消费组+降级直查，验证 2h 恢复"

周四任务2"ID 区转化率也降了"：
1. 任务前：向量检索长期记忆 → 命中周一排障经验 → 直接查快照延迟 → 30 秒定位
2. 任务中：短期工作台记录本次中间态（region=ID、同样延迟但根因=价格配置错）——与旧经验**不同**
3. 任务后：短期清空；长期写入新经验"ID 区根因=价格配置错误"，与 SG 那条并存 → 经验库越用越聪明

反例走查：
- 长期当工作台：任务2 过程中每次查中间状态都去检索长期库 → 慢 + **本次任务新产生的状态还没写入长期库** → 查到的永远是昨天之前的旧快照 → 中途失忆（工作台必须是实时、免检索的短期上下文）
- 短期当长期不清空：任务2 开始时工作台还堆着任务1 的"SG/活动日" → 干扰判断，把任务1 前提当任务2 前提 → 错误归因；上下文越堆越满 → 爆 context（正是本线程遇到的问题）

时机一句话记忆：**任务前=长期检索注入（带经验开场）；任务中=短期工作台（防失忆）；任务后=短期清空+长期沉淀（跨任务积累）。**
